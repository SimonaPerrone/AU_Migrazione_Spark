# Migrazione Spark 2 -> Spark 3 - gsv-gasivori

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`gsv-gasivori` è un job batch Scala/Spark che aggrega consumi gasivori da più sorgenti (richieste, forniture, daily consumption, esclusi, incoerenti).  
Il job applica regole di pulizia e business, genera l’aggregato finale e lo pubblica su Hive/HDFS.  
A valle, uno script Sqoop esporta il risultato verso Oracle.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark 2.4 (`2.4.0.cloudera2`) e Scala 2.11;
- è strutturato in `Driver`, `args`, `controller`, `dao`, `schema`, `utility`;
- viene eseguito via script `run_gsv.sh` con `spark2-submit` e workflow shell + Sqoop.

(Riferimenti: `Documenti per migrazione/2.Migrazione gsv-gasivori.md`, `gsv-gasivori/pom.xml`, `gsv-gasivori/src/main/resources/deploy/*.sh`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: legge i parametri di lancio (es. path properties).
- **`driver`**: avvia e orchestra tutto il job.
- **`factory`**: non presente come package dedicato.
- **`flow`**: non presente come package dedicato; la logica è nei controller.
- **`model`**: rappresentato dagli schemi (`schema/*`).
- **`dao/controller/utility`**: i DAO leggono/scrivono dati, i controller applicano regole, utility gestisce Spark/config/log.

(Riferimenti: `gsv-gasivori/src/main/scala/it/eng/au/gsvAggregatoreConsumi/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x` (se Scala)
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

Motivo: allineamento tecnico all’onboarding CDP 7.1.9 (compatibilità Spark 3, sicurezza Kerberos/CDE, vincoli operativi Data Services).

(Riferimenti: `gsv-gasivori/pom.xml`, `Documenti per migrazione/Documento Onboarding Cloudera CDP 7.1.9 v1.9.md`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.  
[analizza il codice git e descrivi gli step di funzionamento]

| Step | Nome Step | Descrizione Step |
|---|---|---|
| Step1 | Avvio script | `run_gsv.sh` lancia `spark2-submit` con main `it.eng.au.gsvAggregatoreConsumi.Driver`. |
| Step2 | Parsing parametri | `ArgsFactory` legge `-p` (file properties). |
| Step3 | Inizializzazione ambiente | `Environment.getOrCreate(...)` crea SparkSession e carica properties da HDFS/local. |
| Step4 | Lettura input | DAO leggono tabelle GSV (richiesta/forniture) e parquet consumi/esclusi/incoerenti. |
| Step5 | Pulizia consumi | `SterilizationController` normalizza e prepara il dataset di consumo. |
| Step6 | Join business | `JoinRichiesteFornitureController` unisce richieste e forniture. |
| Step7 | Split per tipologia | `SplitRichiesteController` separa ordinarie/suppletive/consuntive. |
| Step8 | Aggregazione | `AggregatoreController` calcola aggregati per ciascun ramo. |
| Step9 | Union finale | I dataset sono uniti con `unionByName`. |
| Step10 | Scrittura output | `GsvConsAggrDAO.writeOnHive` esegue cast tecnici e salva su HDFS/Hive + refresh tabella. |
| Step11 | Export Sqoop | `workflow_gsv.sh` invoca `sqoop-export.sh` verso Oracle. |

(Riferimenti base del flusso: `Driver.scala`, `controller/*.scala`, `dao/gsv/GsvConsAggrDAO.scala`, `deploy/run_gsv.sh`, `deploy/workflow_gsv.sh`, `deploy/sqoop/*.sh`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)
[analizza il file Documento Onboarding Cloudera CDP 7.1.9 v1.9 e descrivi tutte le modifiche che devono essere fatte per far funzionare il progetto sulla nuova piattaforma]

| Modifica | Nome Modifica | Obiettivo | Dove intervenire | Cosa cambiare |
|---|---|---|---|---|
| MOD1 | Upgrade build Spark/Scala | Rendere compilabile/eseguibile su Spark 3 | `gsv-gasivori/pom.xml` | Portare `scala.version` a `2.12.x`, `scala.compat.version` a `2.12`, dipendenze Spark `_2.12` (`spark-core/spark-sql/spark-hive`) su versione Spark3 target, aggiornare scalatest/plugin build. |
| MOD2 | Aggiornamento submit script | Eseguire job su runtime nuovo | `src/main/resources/deploy/run_gsv.sh` | Sostituire `spark2-submit` con submit Spark3; mantenere conf necessarie; verificare `--files` e parametri (`shuffle`, memory overhead, dynamic allocation). |
| MOD3 | Sicurezza YARN (Kerberos) | Conformità onboarding per job su cluster | script di run (`run_gsv.sh`, workflow) | Inserire `set -euo pipefail`, `kinit -kt`, gestione `KRB5CCNAME`, cleanup con `kdestroy` e `trap`. |
| MOD4 | Adattamento CDE Data Services | Compatibilità esecuzione su `spark35-test` | script run + properties | Usare `CDE_CREDENTIALS_FILE` e `CDE_CONFIG_PROFILE`; evitare dipendenze da filesystem locale/NFS per dati; usare HDFS/Object Storage; passare config via `--files`. |
| MOD5 | Verifica codice Spark 3 | Evitare regressioni funzionali | `Driver.scala`, `controller/*.scala`, `dao/gsv/GsvConsAggrDAO.scala` | Validare cast numerici/timestamp, gestione null, comportamento `unionByName`, semantica SQL Spark3; aggiungere `spark.sql.legacy.*` solo temporaneamente se serve. |
| MOD6 | Pulizia conf non supportate CDE | Evitare fallimenti in Data Services | script/conf runtime | Garantire assenza di `spark.shuffle.service.enabled=true` (non supportata in CDE). |
| MOD7 | Hardening Sqoop | Stabilità integrazione Oracle | `deploy/sqoop/*.sh` | Verificare credenziali/JDBC e path HDFS; non usare `--direct` salvo necessità esplicita (onboarding segnala criticità). |
| MOD8 | Revisione path e permessi | Evitare errori I/O in nuovi ambienti | `profiles/*/config.properties`, `deploy/params.properties` | Validare path `deploy.path`, `deploy.path.hdfs`, `hive.*location`, proprietà Oracle, permessi HDFS/Ranger/Kerberos. |

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: oggetto principale Spark per DataFrame/SQL.
- **DAO**: componente che legge/scrive dati da sorgenti/destinazioni.
- **Flow**: sequenza logica di trasformazioni business (qui implementata nei controller).
- **Schema**: struttura delle colonne e dei tipi dati.
- **Idempotenza**: rieseguire il job ottenendo risultato consistente senza effetti collaterali indesiderati.
