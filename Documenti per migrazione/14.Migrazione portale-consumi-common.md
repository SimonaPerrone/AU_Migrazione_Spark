# MIGRAZIONE_SPARK_PORTALE_CONSUMI_COMMON

## 1. Descrizione Progetto

### 1.1 Obiettivo e contesto
`portale-consumi-common` è un progetto di supporto operativo, centrato su script shell e risorse di configurazione condivise (backup/pulizia dati audit).  
Non contiene un job Spark applicativo principale come gli altri progetti di migrazione.

### 1.2 Perimetro funzionale e tecnico
- Script operativi: `backup_collezione.sh`, `pulizia_dati_audit.sh`.
- Configurazioni profilo in `src/main/resources/profiles`.
- Test script documentati in `src/test/sh`.

### 1.3 Architettura logica
- **Core**: script shell di manutenzione.
- **Config**: profili `dev/prod`.
- **Build**: Maven (packaging e copia risorse in deploy).

### 1.4 Tecnologie e dipendenze principali
- Java 8 (config build)
- Scala 2.11 (impostata a livello build, ma senza pipeline Spark applicativa evidente)
- Maven + resources/shade plugin
- Shell scripting

---

## 2. Funzionamento step by step del progetto

1. Il package Maven prepara artefatti e cartella deploy.
2. Gli script vengono eseguiti in ambiente cluster/bastion con configurazioni profilo.
3. `backup_collezione.sh` esegue salvataggio dati secondo parametri previsti.
4. `pulizia_dati_audit.sh` esegue pulizia controllata dati audit.
5. I test shell (`src/test/sh`) coprono casi operativi principali.

## 3. Modifiche da apportare ad ogni singola componente del progetto

### 3.1 `pom.xml`
1. Confermare il ruolo del modulo: utility-only (non Spark job).
2. Se rimane utility-only, semplificare build/plugin non necessari alla migrazione Spark.
3. Allineare versioni plugin Maven a standard piattaforma.

### 3.2 Script (`src/main/resources/deploy`)
1. Hardening error handling (`set -euo pipefail`, exit code espliciti).
2. Validazione argomenti obbligatori e gestione casi null/path mancanti.
3. Uniformare logging e naming output.

### 3.3 Configurazioni (`src/main/resources/profiles`)
1. Verificare coerenza proprietà `dev/prod`.
2. Centralizzare variabili ambientali e path cluster.
3. Validare permessi/utenze tecniche su path di backup e pulizia.

### 3.4 Relazione con migrazione Spark 3
1. Nessuna migrazione API Spark diretta sul codice modulo.
2. Adeguare solo eventuali script che invocano tool cluster cambiati con il passaggio piattaforma.
3. Verificare compatibilità operativa nel nuovo ambiente runtime.

## 4. Test da prevedere

### 4.1 Test unitari/script
1. Test parametrico script con input validi/non validi.
2. Test gestione errori su path inesistenti/permessi negati.
3. Test idempotenza operazioni di cleanup.

### 4.2 Test integrazione
1. Test su ambiente DEV con directory/tabelle mock.
2. Verifica backup e restore tecnico.
3. Verifica pulizia audit senza perdita non prevista.

### 4.3 Test regressione
1. Confronto output/log script pre e post aggiornamenti.
2. Verifica tempi e volumi gestiti.
3. Verifica schedulazione/orchestrazione esistente.

### 4.4 Test operativi
1. Runbook di esecuzione e rollback.
2. Controllo allarmi/monitoring.
3. Validazione con utenza operativa.

## 5. Glossario minimo
- **Utility module**: modulo di supporto senza job Spark core.
- **Hardening**: rafforzamento robustezza script/config.
- **Runbook**: procedura operativa standard.
