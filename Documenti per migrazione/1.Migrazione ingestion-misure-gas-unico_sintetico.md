# Migrazione Spark 2 -> Spark 3 - ingestion-misure-gas-unico

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`ingestion-misure-gas-unico` è un job batch Spark/Scala che gestisce i flussi XML gas (IGMG, IGMR e Standard).  
Legge i file in input, applica controlli di ammissibilità e validazione, trasforma i dati e scrive gli output su Hive.  
In alcuni casi esegue anche export verso sistemi esterni tramite script Sqoop.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark 2 (`spark2-submit`) e Scala 2.11;
- è organizzato in componenti `args`, `driver`, `factory`, `flow`, `model`, `validate`, `utility`;
- usa script deploy e configurazioni ambiente (`config.properties`, `application.conf`, `ammissibilita.conf`).

(Riferimenti: `Documenti per migrazione/1.Migrazione ingestion-misure-gas-unico.md`, `ingestion-misure-gas-unico/pom.xml`, `ingestion-misure-gas-unico/src/main/resources/deploy/*`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: legge i parametri passati a riga di comando.
- **`driver`**: avvia il job e seleziona il tipo di elaborazione.
- **`factory`**: costruisce la logica/flow da usare.
- **`flow`**: contiene le trasformazioni dati principali.
- **`model`**: definisce struttura e schema dei dati.
- **`dao/controller/utility`**: qui presenti soprattutto `utility` + `validate` + `unzip` per funzioni operative e controlli.

(Riferimenti: `ingestion-misure-gas-unico/src/main/scala/it/au/misure/ingestionMisureGasUnico/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x` (se Scala)
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `ingestion-misure-gas-unico/pom.xml`, `Documenti per migrazione/Documento Onboarding Cloudera CDP 7.1.9 v1.9.md`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

| Step | Nome Step | Descrizione Step |
|---|---|---|
| Step1 | Avvio script | `spark-submit-gas-unzip.sh` e `spark-submit-gas-ingestion.sh` avviano i driver con `spark2-submit`. |
| Step2 | Parsing argomenti | `UnzipDriver`/`FlowDriver` leggono i parametri (es. flow name, data run, opzioni). |
| Step3 | Inizializzazione Spark | `Environment.getOrCreate(...)` crea SparkSession e configurazione runtime. |
| Step4 | Pre-check sorgenti | fase unzip: controlli su input e (se abilitato) verifica tabelle Sqoop/RCU aggiornate. |
| Step5 | Lettura input XML | i file decompressi vengono letti e convertiti in strutture intermedie. |
| Step6 | Validazione business | regole di ammissibilità file/PDR nei package `validate` e flow specifici (IGMG/IGMR/Standard). |
| Step7 | Trasformazioni | mapping campi, cast, arricchimenti da tabelle Hive, colonne comuni tecniche. |
| Step8 | Scrittura output | write su tabelle Hive (`insertInto`) e report ammissibilità. |
| Step9 | Export/Supporto | script deploy/sqoop eseguono eventuali passaggi di export verso sistemi esterni. |
| Step10 | Cleanup e log | pulizia file temporanei, log di esito finale. |

(Riferimenti base del flusso: `driver/FlowDriver.scala`, `driver/UnzipDriver.scala`, `flow/Flow.scala`, `flow/IGMGFlow.scala`, `flow/IGMRFlow.scala`, `src/main/resources/deploy/*`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

| Modifica | Nome Modifica | Obiettivo | Dove intervenire | Cosa cambiare |
|---|---|---|---|---|
| MOD1 | Upgrade Spark/Scala | Compatibilità Spark 3 | `pom.xml` | Portare `spark.version` a `3.x`, `scala.version` a `2.12.x`, `scala.minor.version` a `2.12`, dipendenze Spark `_2.12`. |
| MOD2 | Pulizia dipendenze legacy | Evitare incompatibilità | `pom.xml` | Rimuovere `spark-csv` legacy e aggiornare librerie compatibili Spark3 (`spark-xml`, test libs, plugin build). |
| MOD3 | Aggiornamento submit | Eseguire su nuova piattaforma | `deploy/spark-submit-gas-ingestion.sh`, `deploy/spark-submit-gas-unzip.sh` | Sostituire `spark2-submit` con submit Spark3 coerente con ambiente target. |
| MOD4 | Sicurezza YARN | Conformità onboarding | script `.sh` di run | Inserire autenticazione Kerberos (`kinit -kt`, `KRB5CCNAME`, cleanup con `kdestroy`). |
| MOD5 | Adattamento CDE | Eseguibilità su Data Services | script run + conf | Usare `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE`; mantenere config via `--files`. |
| MOD6 | Gestione path dati CDE | Evitare accessi non supportati | `profiles/*/config.properties` e conf deploy | In CDE evitare filesystem locale/NFS per dati; usare path HDFS/Object Storage. |
| MOD7 | Compatibilità Spark SQL | Evitare differenze risultato | `flow/*.scala`, `utility/environment/Environment.scala` | Verificare cast, parsing date/timestamp, null handling, comportamento join/union su Spark3. |
| MOD8 | Legacy config temporanee | Ridurre scostamenti iniziali | conf Spark runtime | Usare solo se necessario `spark.sql.legacy.*` (es. `timeParserPolicy`) e rimuoverle a fine stabilizzazione. |
| MOD9 | Config non supportate CDE | Evitare failure in run CDE | conf submit | Assicurare assenza di `spark.shuffle.service.enabled=true` (non supportata in CDE). |
| MOD10 | Hardening Sqoop | Stabilità integrazione esterna | `deploy/sqoop/*.sh` | Verificare credenziali/JDBC/path; evitare uso `--direct` salvo necessità esplicita. |
| MOD11 | ACL visibilità log/job (CDE) | Operatività team | comando submit CDE | Se necessario, aggiungere `--acl-full-access-*` / `--acl-view-only-*`. |
| MOD12 | TLS/endpoint cluster | Connessioni sicure ai servizi | configurazioni JDBC/Hive/Impala | Allineare truststore/certificati/endpoint come da onboarding CDP 7.1.9. |

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: elaborazione dati a blocchi con inizio/fine esecuzione.
- **SparkSession**: entrypoint principale Spark per DataFrame e SQL.
- **DAO**: componente che incapsula lettura/scrittura dati.
- **Flow**: blocco logico di trasformazioni business.
- **Schema**: struttura colonne e tipi del dataset.
- **Idempotenza**: rieseguire il job senza effetti collaterali non voluti.
