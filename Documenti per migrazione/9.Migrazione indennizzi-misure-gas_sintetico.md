# Migrazione Spark 2 -> Spark 3 - indennizzi-misure-gas

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`indennizzi-misure-gas` è una suite multi-modulo per gestire l’intero processo indennizzi: calcolo, verifica ammissibilità rendiconti, pubblicazione risultati e pubblicazione rendiconti.

In pratica:
1. calcola gli indennizzi,
2. valida i rendiconti,
3. pubblica dati finali per i sistemi a valle.

### 1.2 Cosa sappiamo oggi dal documento esistente

Il progetto:
- è multi-modulo Maven,
- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8,
- ha i moduli:
  - `indennizzi-misure-gas-common`
  - `calcolo-indennizzi`
  - `ammissibilita-rendiconti`
  - `pubblicazione-indennizzi`
  - `pubblicazione-rendiconti`.

### 1.3 Significato dei componenti (in parole non tecniche)

- **Driver (per modulo)**: avvia e orchestra i passaggi.
- **args**: legge parametri di lancio.
- **controller**: applica regole business.
- **dao**: legge/scrive dati da sorgenti e target.
- **model/schema**: struttura dati.
- **deploy/**: script run/spark-submit/params/logging.

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale:
- Spark `2.4.0.cloudera2`
- Scala `2.11.12`
- Build Maven multi-modulo

Target:
- Spark 3.x
- Scala 2.12.x
- aggiornamento script runtime e compatibilità SQL Spark 3.

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` root + moduli - cosa cambiare, dove, e perché

### Obiettivo

Allineare tutta la suite a Spark 3 e Scala 2.12.

### Checklist operativa

1. Root `pom.xml`: upgrade `spark.version`, `scala.version`, `scala.compat.version`.
2. Moduli: aggiornare artifact Spark `_2.12`.
3. Aggiornare librerie test/plugin (ScalaTest, Surefire, scala-maven-plugin).
4. Verificare dipendenze comuni (`common`) e serializzazione.

### Errori tipici da principiante

- aggiornare solo root ma non i pom modulo;
- tenere librerie `_2.11` nel classpath.

---

## 3.2 Codice Scala (Driver/controller/dao) - cosa controllare concretamente

### Obiettivo

Garantire compatibilità Spark 3 mantenendo il comportamento business.

### Dove intervenire prima

1. `calcolo-indennizzi` (modulo più centrale),
2. `ammissibilita-rendiconti`,
3. `pubblicazione-indennizzi` e `pubblicazione-rendiconti`.

### Cosa cambiare (pratico)

- verificare cast/date/null/join con semantica Spark 3,
- verificare query SQL/Hive,
- controllare eventuale serializzazione custom e UDF.

### Config transitoria utile

- eventuali `spark.sql.legacy.*` solo temporaneamente.

### Errori tipici da principiante

- migrare tutti i moduli insieme senza baseline intermedia;
- non confrontare output modulo per modulo.

---

## 3.3 Configurazione runtime (properties + script)

### Obiettivo

Eseguire i moduli su Spark 3 senza rompere l’operatività.

### Cosa verificare

1. `run-ammissibilita-rendiconti*.sh`
2. `run-pubblicazione-indennizzi.sh`
3. `run-pubblicazione-rendiconti.sh`
4. script `spark-submit` e cartelle `deploy/hive`
5. `params.properties` e profili.

### Errori tipici da principiante

- aggiornare il codice e lasciare script submit legacy;
- disallineamento conf tra moduli.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna root + pom dei moduli.
2. Migra e valida `calcolo-indennizzi`.
3. Migra `ammissibilita-rendiconti`.
4. Migra i due moduli di pubblicazione.
5. Aggiorna script deploy.
6. Esegui regressione end-to-end.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- test environment/driver per modulo (`EnvironmentSparkTest`),
- test controller/dao presenti nei moduli.

## 4.2 Integration test - test end-to-end

- pipeline completa: calcolo -> ammissibilità -> pubblicazioni,
- confronto Spark2 vs Spark3 su record count, KPI, schema output.

## 4.3 Test non funzionali

- tempi run per modulo,
- stabilità su run ripetute,
- verifica recovery dove previsto (es. `recovery.csv`).

## 4.4 Criteri di accettazione finali

1. Output business coerente col legacy
2. Nessun errore runtime Spark 3
3. Esecuzione stabile dei 4 moduli operativi principali.
