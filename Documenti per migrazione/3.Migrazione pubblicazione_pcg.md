# Migrazione Spark -&gt; Spark 3 - pubblicazione\_pcg

## 1. Descrizione Progetto

### 1.1 A cosa serve questo job (spiegazione semplice)

`pubblicazione_pcg` è un job batch che legge dati di consumo giornaliero (`dailyConsumption`), applica regole di trasformazione business e produce un output finale da pubblicare/consumare da sistemi a valle.

In termini pratici:

1. legge i dati di ingresso,

2. prepara i parametri temporali della run,

3. esegue le trasformazioni,

4. scrive i risultati.

### 1.2 Perché questo progetto è più delicato degli altri

Questo progetto parte da uno stack \*\*molto vecchio\*\*:

- Spark `1.6.0-cdh5.14.2`

- Scala `2.10.5`

- Java `1.8`

- dipendenza legacy `spark-csv_2.10`

Quindi la migrazione non è solo “upgrade versione”: è una migrazione \*\*strutturale\*\* (API, build, dipendenze, runtime).

### 1.3 Componenti logici coinvolti

- \*\*Driver\*\*: punto di ingresso (`main`), orchestration del flusso.

- \*\*ParseCLIArgs / args\*\*: lettura parametri passati al job.

- \*\*DAO (`DailyConsumptionDAO`)\*\*: lettura dati sorgente.

- \*\*Controller/servizio (`PubblicazionePCG`)\*\*: logica business e trasformazioni.

- \*\*Output layer\*\*: scrittura risultato finale.

### 1.4 Obiettivo finale della migrazione

Portare il job su Spark 3 mantenendo il comportamento funzionale atteso:

- stessi risultati di business (o differenze minime documentate),

- nessun uso di API Spark 1.x non supportate,

- esecuzione stabile su runtime moderno.

## 2. Funzionamento step by step

### Step 1 - Avvio job

Parte `Driver.main`.  

Vengono letti i parametri CLI (es. data run, ambiente, opzioni operative).

### Step 2 - Inizializzazione contesto Spark

Il job inizializza il contesto di elaborazione (in legacy spesso SQLContext/HiveContext).  

Nella migrazione andrà uniformato a `SparkSession`.

### Step 3 - Calcolo variabili temporali

Vengono calcolate variabili come `date.run` e `year.month` con offset mese.  

Questa fase è critica perché influenza sia filtri dati sia naming/partizionamento output.

### Step 4 - Lettura input da DAO

`DailyConsumptionDAO` legge il dataset sorgente.

### Step 5 - Esecuzione logica business

Il Driver passa i dati a `PubblicazionePCG.run(...)`, dove sono applicate le regole di trasformazione.

### Step 6 - Produzione output

Viene costruito il dataset finale nel formato atteso.

### Step 7 - Scrittura e chiusura

Il job scrive il risultato e produce log di fine processo.

## 3. Modifiche da apportare per componente (molto dettagliate, livello principiante)

## 3.1 `pom.xml` (migrazione maggiore)

### Obiettivo

Adeguare build e dipendenze al nuovo stack Spark 3 + Scala 2.12.

### Cosa fare, in ordine

1. Aggiorna versioni base:

   - Scala: `2.10` -&gt; `2.12.18`

   - Spark: `1.6` -&gt; `3.5.x`

2. Aggiorna artifact Spark con suffisso `_2.12`:

   - `spark-core_2.12`

   - `spark-sql_2.12`

   - `spark-hive_2.12`

3. Rimuovi `spark-csv_2.10` (legacy) e usa CSV nativo Spark SQL.

4. Aggiorna librerie test (specs2/scalatest) compatibili con Scala 2.12.

5. Verifica plugin Maven (`scala-maven-plugin`, `surefire`, eventuale `shade`).

### Errori tipici da evitare

- Restare con artifact `_2.10` o `_2.11`.

- Aggiornare Spark ma non Scala.

- Ignorare conflitti di dipendenze in build (poi errori runtime).

---

## 3.2 Codice Scala (`Driver`, `controller`, `dao`, `utility`)

### Obiettivo

Sostituire pattern Spark 1.x non compatibili con Spark 3.

### Interventi principali

1. \*\*Contesto Spark\*\*

   - prima: `SQLContext/HiveContext`

   - dopo: `SparkSession`

2. \*\*API DataFrame/Dataset\*\*

   - controllare trasformazioni che usano API rimosse/deprecate.

3. \*\*Date/time parsing\*\*

   - Spark 3 è più rigoroso: rendere espliciti i formati data/timestamp.

4. \*\*Cast e null handling\*\*

   - esplicitare cast colonne,

   - gestire null in filtri/join in modo robusto.

5. \*\*RDD legacy\*\*

   - se presenti pipeline molto RDD-centriche, valutarne migrazione a DataFrame per compatibilità/manutenibilità.

### Strategia pratica per principiante

- Prima fai compilare.

- Poi risolvi errori di API uno a uno.

- Poi controlla differenze funzionali su dataset piccolo.

---

## 3.3 DAO e accesso dati

### Cosa verificare

- lettura `dailyConsumption` con schema coerente;

- formati data/numero espliciti;

- gestione colonne opzionali/null.

### Perché è importante

Molti problemi di migrazione non nascono dalla business logic, ma da inferenza schema diversa tra Spark 1.x e Spark 3.

---

## 3.4 Configurazione runtime (`spark-submit`, conf Spark SQL)

### Cosa rivedere

1. script di submit (class, jar, parametri, conf),

2. compatibilità con cluster manager target,

3. conf Spark SQL:

   - `spark.sql.adaptive.enabled`

   - `spark.sql.shuffle.partitions`

   - eventuali `spark.sql.legacy.*` solo temporanei.

### Buona pratica

Usa flag `legacy` solo per allineare i risultati nella fase iniziale, poi rimuovili gradualmente.

---

## 3.5 Compatibilità Hive/output

### Controlli obbligatori

- schema output identico (o con differenze documentate),

- formati file attesi,

- partizionamento coerente,

- compatibilità con consumer downstream.

---

## 3.6 Sequenza consigliata di migrazione (operativa)

1. Aggiorna `pom.xml`.

2. Porta build in compilazione.

3. Refactor API Spark 1.x -&gt; Spark 3.

4. Aggiorna submit/conf runtime.

5. Esegui test unit/integration.

6. Confronta output con baseline legacy.

7. Promuovi progressivamente in ambienti superiori.

---

## 4. Test da prevedere (in chiaro)

## 4.1 Unit test

- calcolo `year.month` e offset mese,

- regole business in `PubblicazionePCG`,

- comportamento DAO con input mock.

## 4.2 Integration test (obbligatori)

Esecuzione completa su sample storico:

- record count,

- checksum/controlli su chiavi business,

- qualità colonne critiche.

## 4.3 Test di compatibilità

- lettura/scrittura su stessi path/tabelle attesi,

- schema compatibile con consumer,

- riesecuzione stesso mese (idempotenza).

## 4.4 Test non funzionali

- tempi di esecuzione,

- uso memoria/shuffle,

- stabilità su run ripetute.

## 4.5 Criteri di accettazione

La migrazione è approvata se:

1. output funzionalmente equivalente al legacy,

2. nessun uso residuo di API Spark 1.x,

3. run stabili in ambiente Spark 3.

---

## 5. Glossario base (per orientarti)

- \*\*Batch\*\*: job che elabora un blocco dati e termina.

- \*\*SparkSession\*\*: oggetto principale Spark per DataFrame/SQL.

- \*\*DAO\*\*: classe che legge/scrive dati.

- \*\*Schema\*\*: struttura colonne + tipi.

- \*\*Idempotenza\*\*: stessa run ripetuta non crea incoerenze.

- \*\*Baseline\*\*: risultato di riferimento (prima della migrazione).
