# Migrazione Spark 2 -> Spark 3 - portale-consumi

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`portale-consumi` è il progetto storico con tool CLI `FlussoMisureTool`.
Gestisce molte funzioni: decompressione, ingestion, ammissibilità, aggregazioni, SEM, commit e procedure portale/export.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è legacy con modulo `flusso-misure-master`;
- usa Spark `1.6.0-cdh5.12.1`, Scala `2.10.x` (non Spark2);
- entrypoint `it.au.misure.cli.FlussoMisureTool`;
- script principali `flusso-misure-pc.sh`, `flusso-misure-pc2.sh`;
- contiene dipendenze legacy (`spark-assembly_2.10`, `spark-xml_2.10`).

(Riferimenti: `Documenti per migrazione/30.Migrazione portale-consumi.md`, `flusso-misure-master/pom.xml`, `FlussoMisureTool.scala`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: opzioni CLI e comandi operativi.
- **`driver`**: il tool CLI decide cosa lanciare.
- **`factory`**: dispatch logico dei comandi.
- **`flow`**: comandi per ingestion/ammissibilità/aggregazioni/SEM/portale.
- **`model`**: dati di input/output per i comandi.
- **`dao/controller/utility`**: implementazioni specifiche per ciascun comando.

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `1.6.0-cdh5.12.1`
- Scala/Python: `Scala 2.10.5/2.10.6`
- Java: `8`
- Build tool: `Maven` legacy

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9

**Nota:** qui la migrazione è di fatto **Spark1 -> Spark3**, quindi più ampia e rischiosa.

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare una base Spark1 legacy a Spark3 moderno.

### Checklist operativa

1. Spark 1.6 -> Spark 3.5
2. Scala 2.10 -> 2.12
3. rimuovere `spark-assembly_2.10` e dipendenze obsolete
4. aggiornare plugin maven/scala
5. verificare tutto il packaging CLI.

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Rendere compatibili tutti i comandi del CLI dispatcher.

### Dove intervenire prima

1. `FlussoMisureTool`;
2. comandi core (ingestion/ammissibilità/aggregazioni);
3. comandi portale/export.

### Cosa cambiare (pratico)

- API Spark legacy -> API Spark3;
- date parser e null semantics;
- eventuali componenti deprecati da riscrivere.

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Stabilizzare run in ambiente CDP.

### Cosa verificare

1. submit e conf Spark3;
2. classpath JDBC esterni;
3. Kerberos valido su YARN;
4. in CDE usare `CDE_CREDENTIALS_FILE` / `CDE_CONFIG_PROFILE`;
5. distribuire conf via `--files` e rimuovere dipendenze locali.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra core build/toolchain.
2. Migra dispatcher CLI.
3. Migra comandi core.
4. Migra comandi secondari.
5. Aggiorna script.
6. Testa comando per comando.

## 5. Glossario minimo (per orientarti subito)

- **CLI tool**: applicazione da riga di comando.
- **Dispatcher**: seleziona il comando da eseguire.
- **Flow legacy**: logica sviluppata su stack vecchio.
- **Toolchain**: versione combinata di Spark/Scala/Build.
- **Refactoring**: riscrittura controllata per compatibilità.
- **Idempotenza**: rilancio con stesso risultato.
