# Migrazione Spark 2 -> Spark 3 - ee_switching

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`ee_switching` gestisce flussi switching elettrico in due modalità principali:
- **funzionali**
- **storici**

Supporta run ordinaria o run parametrica (timestamp, liste POD/distributori/UDD/date), con generazione file XML/ZIP e script di caricamento/pubblicazione.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark `2.4.0.cloudera2` e Scala `2.11.12`;
- ha entrypoint `it.au.misure.ee_switching.driver.FlowDriver`;
- usa `FlowArgsFactory` + `FlowFactory` (`FunzionaliFlow`, `StoriciFlow`);
- ha molti script deploy/load/file/oozie/hql.

(Riferimenti: `Documenti per migrazione/17.Migrazione ee_switching.md`, `ee_switching/pom.xml`, `FlowDriver.scala`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parse e validazione avanzata input run.
- **`driver`**: seleziona flow richiesto e avvia elaborazione.
- **`factory`**: `FlowFactory` mappa nome flow -> implementazione.
- **`flow`**: `FunzionaliFlow` e `StoriciFlow`.
- **`model`**: strutture argomenti/config runtime.
- **`dao/controller/utility`**: pacchetti supporto filtri, letture/scritture, utility.

(Riferimenti: `src/main/scala/it/au/misure/ee_switching/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `ee_switching/pom.xml`, `deploy/spark-submit-ee-switching-generazione-file.sh`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Script submit (`spark-submit-ee-switching-generazione-file.sh`) avvia `FlowDriver`.

### Step 2 - Lettura parametri e config

`FlowArgsFactory.parse/getInputArgs/checkInputArgs` valida combinazioni input (timestamp/liste/date).

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate(...)` inizializza contesto Spark.

### Step 4 - Lettura input

Il flow legge dati switching da Hive e file parametrici HDFS.

### Step 5 - Pulizia e normalizzazione

Normalizza liste, date, timestamp e applica filtri perimetro.

### Step 6 - Regole di business (flow)

`FlowFactory` sceglie:
- `FunzionaliFlow`
- `StoriciFlow`

### Step 7 - Costruzione dataset finale

Produzione dataset output per flussi/finestra richiesta.

### Step 8 - Scrittura output

Scrittura output e generazione XML/ZIP secondo config deploy.

### Step 9 - Chiusura e logging

Log run e script post-elaborazione (load/file/oozie).

(Riferimenti base del flusso: `driver/FlowDriver.scala`, `args/FlowArgsFactory.scala`, `factory/FlowFactory.scala`, script deploy)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Allineare job switching a Spark3/Scala2.12.

(Riferimento: `ee_switching/pom.xml`)

### Checklist operativa

1. Spark -> `3.5.x`
2. Scala -> `2.12.x` (`scala.minor.version=2.12`)
3. Aggiorna artifact `_2.12`
4. Verifica dipendenze (`spark-xml`, `scopt`, test libs)
5. Aggiorna plugin build/test.

### Errori tipici da principiante

- lasciare dipendenze test `spark-csv` legacy;
- mismatch tra scala.minor.version e artifact;
- non verificare librerie XML.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Mantenere run ordinaria/parametrica e i due flow con output equivalenti.

(Riferimento: `FlowDriver.scala`, `FlowArgsFactory.scala`, `flow/*`)

### Dove intervenire prima

1. parsing/validazione args
2. flow funzionali/storici
3. utility filtri e output

### Cosa cambiare (pratico)

- verificare parser date/timestamp e null handling;
- verificare trasformazioni DataFrame/SQL in Spark3;
- controllare schema output XML/ZIP.

### Config transitoria utile

- eventuali `spark.sql.legacy.*` solo temporanee.

### Errori tipici da principiante

- rompere vincoli input del parser;
- non testare run con due date storiche consecutive.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Far funzionare script switching su CDP 7.1.9.

(Riferimento: `profiles/prod/config.properties`, `deploy/conf/application.conf`, script deploy)

### Cosa verificare

1. submit Spark3 al posto di `spark2-submit`;
2. conf risorse (`executors`, `memory`, `queue`);
3. path XSD, output ZIP/XML, HDFS deploy;
4. script integrati (`ee-switching-load*.sh`, `ee-switching-file*.sh`).

### Errori tipici da principiante

- non aggiornare script secondari;
- queue/path errati per ambiente;
- conf non supportate in CDE.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna pom.
2. Migra parser/driver/factory.
3. Migra flow funzionali/storici.
4. Aggiorna script deploy.
5. Esegui test run ordinaria + parametrica.
6. Promuovi in QA/cluster.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parse/validazione combinazioni input;
- utility filtri date/liste;
- trasformazioni isolate.

## 4.2 Integration test - test end-to-end

- run ordinaria funzionali;
- run ordinaria storici;
- run parametrica con timestamp e liste;
- confronto Spark2 vs Spark3 su output e schema.

(Riferimento: `flow/FunzionaliFlow.scala`, `flow/StoriciFlow.scala`)

## 4.3 Test non funzionali

- performance su run completi;
- stabilità run ripetute;
- idempotenza output.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline ee_switching)

## 5. Glossario minimo (per orientarti subito)

- **Run ordinaria**: esecuzione standard senza filtri estesi.
- **Run parametrica**: esecuzione pilotata da file input (date/liste/timestamp).
- **Flow funzionali/storici**: due modalità logiche di elaborazione.
- **XSD**: schema XML per validare tracciati.
- **Idempotenza**: riesecuzione con risultato coerente.
- **Queue**: coda cluster per risorse Spark.
