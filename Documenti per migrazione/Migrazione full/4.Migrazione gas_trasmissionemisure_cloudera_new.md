# Migrazione Spark 2 -> Spark 3 - gas_trasmissionemisure_cloudera

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`gas_trasmissionemisure_cloudera` è un job batch PySpark che legge file XML di misure gas, valida nomenclatura e tracciato XSD, trasforma i contenuti per diversi flussi e scrive output su Hive/HDFS.  
In pratica:
1. recupera lista file da query,
2. valida i file,
3. estrae e trasforma i record,
4. pubblica dettaglio + tabella principale.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è Python/PySpark con entrypoint `source/pyspark2/Main.py`;
- usa API legacy Spark (`SparkContext`, `SQLContext`, `HiveContext`);
- gestisce validazioni file (nomenclatura + XSD) e scritture parquet con `MSCK REPAIR TABLE`.

(Riferimenti: `Documenti per migrazione/4.Migrazione gas_trasmissionemisure_cloudera.md`, `source/pyspark2/Main.py`, `source/pyspark2/Ingestion.py`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parsing parametri CLI (`Main.py`, `Params.py`).
- **`driver`**: entrypoint applicativo (`Main.py`) che avvia l’ingestion.
- **`factory`**: non presente come package dedicato.
- **`flow`**: logica di flusso gestita via `selectorFlusso.py` e package `flussi`.
- **`model`**: non presente come package dedicato; strutture costruite durante parsing XML.
- **`dao/controller/utility`**: non formalizzati come in progetti Scala; logica concentrata in `Ingestion.py` + moduli helper.

(Riferimenti: `source/pyspark2/{Main.py,Params.py,Ingestion.py,selectorFlusso.py,flussi/*}`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: pattern legacy pre-Spark3 (inizializzazione con SparkContext/HiveContext)
- Scala/Python: Python (job PySpark legacy)
- Java: runtime cluster legacy (non fissato nel repo)
- Build tool: script shell + zip Python (non Maven in questo progetto)

Target:

- Spark: `3.x`
- Scala: `2.12.x` (se Scala) — non applicabile direttamente (progetto PySpark)
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `source/pyspark2/script/*.sh`, onboarding `Documento Onboarding Cloudera CDP 7.1.9 v1.9.md`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Lo script `source/pyspark2/script/ingestion_data_flussi2.sh` prepara zip sorgenti Python e lancia `spark-submit` su `Main.py`.

### Step 2 - Lettura parametri e config

`Main.py` legge opzioni (`-m`, `-f`, `-q`, `-e`, `--anno`, `--mese`, `--giorno`, `-t`, `-v`) e costruisce `Params`.

### Step 3 - Inizializzazione Spark

`Ingestion.set_spark_context(...)` crea `SparkConf`, `SparkContext` e `HiveContext` (con fallback `SQLContext`), poi imposta conf SQL/Hive.

### Step 4 - Lettura input

Esegue la query SQL (inline o da file), ottiene la lista file, filtra per flusso e legge i contenuti con `wholeTextFiles`.

### Step 5 - Pulizia e normalizzazione

Decodifica UTF-8, parsing XML, preparazione record intermedi.

### Step 6 - Regole di business (flow)

Applica:
- validazione nomenclatura (`valida_nomenclatura`),
- validazione XSD (`valida_flussoXSD`),
- parsing per flusso (`selectorFlusso`),
- separazione validi/non validi.

### Step 7 - Costruzione dataset finale

Costruisce record dettaglio per cod_flusso e record principali con metadati file/esito/causali.

### Step 8 - Scrittura output

Scrive parquet partizionato su HDFS e lancia `MSCK REPAIR TABLE` sulla tabella target.

### Step 9 - Chiusura e logging

Log di fine elaborazione e terminazione run.

(Riferimenti base del flusso: `source/pyspark2/{Main.py,Ingestion.py,selectorFlusso.py}`, `source/pyspark2/script/*.sh`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 Script di esecuzione (`spark-submit`) - cosa cambiare, dove, e perché

### Obiettivo

Allineare l’avvio job al runtime CDP 7.1.9 Spark3.

(Riferimento: `source/pyspark2/script/ingestion_data_flussi2.sh`, onboarding CDP)

### Checklist operativa

1. Aggiorna submit per Spark3 target (YARN Spark3 o CDE `spark35-test`).
2. YARN: integra autenticazione Kerberos (`kinit -kt`, `KRB5CCNAME`, cleanup).
3. CDE: usa `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE`.
4. Mantieni `--files` per config/log4j.
5. Evita conf non supportate CDE (`spark.shuffle.service.enabled=true`).

### Errori tipici da principiante

- migrare codice ma lasciare script submit legacy;
- dimenticare autenticazione Kerberos/CDE;
- usare path locali/NFS dati in CDE.

---

## 3.2 Codice PySpark (`Ingestion.py`, `Main.py`, `selectorFlusso.py`) - cosa controllare concretamente

### Obiettivo

Rendere il codice compatibile con Spark 3 mantenendo la logica funzionale.

(Riferimento: `source/pyspark2/*.py`)

### Dove intervenire prima

1. `Ingestion.py` (bootstrap Spark + pipeline principale)
2. `Main.py` (arg parsing/validazioni)
3. `selectorFlusso.py` e `flussi/*` (logiche specifiche flusso)

### Cosa cambiare (pratico)

- Sostituire inizializzazione legacy (`SparkContext/HiveContext`) con `SparkSession`.
- Verificare comportamento funzioni SQL/Hive (`SHOW PARTITIONS`, `MSCK REPAIR TABLE`).
- Rendere espliciti cast/date parsing e gestione null.
- Verificare UDF/serializzazione e gestione XML su Spark3.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` (solo ponte, poi rimuovere)
- eventuali altre `spark.sql.legacy.*` solo se necessarie

### Errori tipici da principiante

- fermarsi alla compilazione/avvio senza confronto output;
- non testare i flussi separatamente (A01/A40/D01/SM1).

## 3.3 Configurazione runtime (properties + script)

### Obiettivo

Far girare correttamente il job su cluster Spark 3.

(Riferimento: `source/conf/*.json`, `source/pyspark2/script/*.sh`, onboarding CDP)

### Cosa verificare

1. Script `spark-submit` (class/py-file, conf, risorse, path).
2. Parametri SQL (`spark.sql.adaptive.enabled`, `spark.sql.shuffle.partitions`, ecc.).
3. Compatibilità Hive Metastore/runtime target.
4. Path e permessi input/output/warehouse.

### Errori tipici da principiante

- mismatch tra query/path e tabelle target;
- conf Spark valide su cluster legacy ma non su CDP/CDE;
- pipeline che fallisce solo in scrittura finale per partizioni/metastore.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna script submit + sicurezza (Kerberos/CDE).
2. Migra bootstrap Spark a `SparkSession`.
3. Valida lettura query + wholeTextFiles + parsing XML.
4. Valida validazioni nomenclatura/XSD.
5. Valida scrittura parquet + repair table.
6. Esegui regressione su più flussi e poi tuning performance.

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: oggetto principale per usare Spark SQL/DataFrame.
- **DAO**: componente che legge/scrive dati da/verso sorgenti (qui non formalizzato come package).
- **Flow**: sequenza di trasformazioni business per flusso.
- **Schema**: struttura colonne + tipi di un dataset.
- **Idempotenza**: rieseguire il job senza effetti collaterali non voluti.
