# Migrazione Spark 2 -> Spark 3 - meccanismo-incentivante-distributori-gas

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`meccanismo-incentivante-distributori-gas` (MID) gestisce più flussi legati al meccanismo incentivante:
- calcolo `SBG`, `AGG`, `AGG_BIT`,
- predisposizione `MID1_PREP`, `MID2_PREP`,
- pubblicazione `MID1_PUBB`, `MID2_PUBB`.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8;
- ha entrypoint `it.eng.au.mid.Driver`;
- valida il flow con `ArgsFactory`;
- usa run script dedicati (`run_mid_agg_standard.sh`, `run_mid_sbg_standard.sh`, `run_mid1_preparazione.sh`, ecc.);
- tutti gli script usano `spark2-submit`.

(Riferimenti: `Documenti per migrazione/25.Migrazione meccanismo-incentivante-distributori-gas.md`, `meccanismo-incentivante-distributori-gas/*`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: legge path properties e flow richiesto.
- **`driver`**: avvia Spark e instrada al flow corretto.
- **`factory`**: validazione flow tramite elenco ammesso.
- **`flow`**: package `flow/calcolo` e `flow/pubblicazione`.
- **`model`**: oggetti argomento e dominio MID.
- **`dao/controller/utility`**: supporto letture/scritture, log, versioning.

(Riferimenti: `Driver.scala`, `args/ArgsFactory.scala`, `flow/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE)

(Riferimenti: `meccanismo-incentivante-distributori-gas/pom.xml`, `deploy/run_mid_*.sh`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Uno script MID avvia `it.eng.au.mid.Driver` con `-p` e `-f`.

### Step 2 - Lettura parametri e config

`ArgsFactory` valida che il flow sia tra quelli supportati.

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate(...)` apre contesto Spark con app name dinamico.

### Step 4 - Lettura input

Ogni flow legge i propri input da tabelle/path configurati.

### Step 5 - Pulizia e normalizzazione

Controlli e normalizzazioni per il ramo di calcolo o pubblicazione.

### Step 6 - Regole di business (flow)

`Driver` esegue uno tra:
- `SbgStandardFlow`, `AggStandardFlow`, `AggBackInTimeFlow`
- `PredisposizioneMid1Flow`, `PredisposizioneMid2Flow`
- `PubblicazioneMid1Flow`, `PubblicazioneMid2Flow`

### Step 7 - Costruzione dataset finale

Costruzione dataset/file intermedi/finali per il flow selezionato.

### Step 8 - Scrittura output

Persistenza output e file zip/pubblicazioni MID dove previsto.

### Step 9 - Chiusura e logging

Chiusura con log di esecuzione e tracciamento versione.

(Riferimenti base del flusso: `Driver.scala`, `ArgsFactory.scala`, script deploy)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Migrare tutti i flow MID a Spark3 in maniera uniforme.

(Riferimento: `meccanismo-incentivante-distributori-gas/pom.xml`)

### Checklist operativa

1. Spark -> `3.5.x`
2. Scala -> `2.12.x`
3. artifact Spark `_2.12`
4. aggiornare test/plugin build
5. verificare compatibilità `kryo-serializers`.

### Errori tipici da principiante

- lasciare un flow compilabile e altri no;
- non riallineare dipendenze di test;
- dimenticare plugin scala.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Mantenere invariato il comportamento dei 7 flow MID.

(Riferimento: `Driver.scala`, `flow/calcolo/*`, `flow/pubblicazione/*`)

### Dove intervenire prima

1. parser args + driver dispatch;
2. flow di calcolo;
3. flow predisposizione/pubblicazione.

### Cosa cambiare (pratico)

- cast e date parsing Spark3;
- null handling su join/filter;
- verifica schema output (soprattutto flow pubblicazione).

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` solo temporaneo.

### Errori tipici da principiante

- testare solo `AGG`;
- non verificare flussi `MID1/MID2` end-to-end.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire i run MID su CDP 7.1.9 in modo stabile.

(Riferimento: `deploy/run_mid_agg_standard.sh`, `run_mid_sbg_standard.sh`, `run_mid1_preparazione.sh`, ecc.)

### Cosa verificare

1. migrare tutti gli script `spark2-submit` -> submit Spark3;
2. riallineare conf risorse e dynamic allocation;
3. Kerberos ticket valido su YARN (`kinit -kt`);
4. in CDE usare credenziali/profile CDE;
5. distribuire config con `--files` e evitare dipendenze da FS locale.

### Errori tipici da principiante

- migrare solo alcuni script MID;
- usare parametri memoria non coerenti tra flow;
- non verificare output file zip finali.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna pom/dependency.
2. Migra args+driver.
3. Migra flow calcolo.
4. Migra flow predisposizione/pubblicazione.
5. Aggiorna script runtime.
6. Testa tutti i flow MID.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- validazione flow in input;
- utility e funzioni trasformazione;
- componenti comuni.

## 4.2 Integration test - test end-to-end

- run completo `SBG`, `AGG`, `AGG_BIT`;
- run completo `MID1_PREP/MID1_PUBB`;
- run completo `MID2_PREP/MID2_PUBB`;
- confronto Spark2 vs Spark3 su KPI/output.

(Riferimento: branch flow nel driver)

## 4.3 Test non funzionali

- benchmark performance per flow pesanti;
- stabilità run ripetute;
- idempotenza e recovery.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline MID corrente)

## 5. Glossario minimo (per orientarti subito)

- **Flow MID**: variante operativa del processo incentivante.
- **Predisposizione**: preparazione dati/file prima della pubblicazione.
- **Pubblicazione**: produzione output finale per consumo esterno.
- **AGG_BIT**: calcolo AGG back-in-time.
- **Driver**: avvio e instradamento del processo.
- **Idempotenza**: riesecuzione coerente.
