# Migrazione Spark 2 -> Spark 3 - partition-optimization

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`partition-optimization` ottimizza e governa partizioni di tabelle Hive/HDFS con 3 job distinti:

1. **repartition**: riscrive le partizioni con numero file/partizioni più efficiente  
2. **rollback**: ripristina i dati dal backup `_backup`  
3. **delete-backup**: elimina i backup dopo verifica

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è Maven multi-modulo (`repartition`, `rollback`, `delete-backup`);
- usa Spark `2.4.0.cloudera2` e Scala `2.11.12`;
- ha script deploy separati (`run_optimize_partition.sh`, `run_optimize_rollback.sh`, `run_optimize_delete_backup.sh`).

(Riferimenti: `Documenti per migrazione/10.Migrazione partition-optimization.md`, `partition-optimization/pom.xml`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: path file properties passato allo startup.
- **`driver`**: coordina l’operazione del modulo (optimize/rollback/delete-backup).
- **`factory`**: non presente.
- **`flow`**: logica in `Driver.scala` + `FunctionUtility.scala`.
- **`model`**: non presente come package dedicato.
- **`dao/controller/utility`**: utility comuni (`Environment`, `FunctionUtility`, `VersionLoggingUtility`).

(Riferimenti: `partition-optimization-repartition/src/main/scala/it/eng/au/partitionOptimization/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven` multi-modulo

Target:

- Spark: `3.x` (raccomandato `3.5.x`)
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `partition-optimization/pom.xml`, moduli `*/pom.xml`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

L’operatore esegue uno dei tre script deploy del modulo desiderato.

### Step 2 - Lettura parametri e config

Viene letto `params.properties` (es. `tables.to.optimize`, `max.optimal.size`, `check.integrity.table`) e config profilo (`root.path.files`, `path.properties`).

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate(...)` inizializza Spark e filesystem.

### Step 4 - Lettura input

Per ogni tabella:
- legge partizioni (`SHOW PARTITIONS`);
- recupera path tabella (`DESC FORMATTED` o utility equivalente);
- legge parquet partizionati.

### Step 5 - Pulizia e normalizzazione

Il job usa `mergeSchema=true` e prepara partizioni/schemi per riscrittura o confronto.

### Step 6 - Regole di business (flow)

- **repartition**: crea backup, ottimizza ogni partizione, opzionalmente controlla integrità.
- **rollback**: sposta `${tablePath}_backup` su path originale.
- **delete-backup**: elimina `${tablePath}_backup`.

### Step 7 - Costruzione dataset finale

Nel repartition produce nuovi parquet ottimizzati nel path originale.

### Step 8 - Scrittura output

Scrittura parquet + script `msck_repair_table.sh` (pre/post nel repartition e nel rollback).

### Step 9 - Chiusura e logging

Log per ogni tabella/partizione e outcome finale.

(Riferimenti base del flusso:  
`partition-optimization-repartition/.../Driver.scala`,  
`partition-optimization-rollback/.../Driver.scala`,  
`partition-optimization-delete-backup/.../Driver.scala`,  
script deploy `run_optimize_*.sh`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare tutti e 3 i moduli a Spark 3 in modo consistente.

(Riferimento: `partition-optimization/pom.xml` + `partition-optimization-*/pom.xml`)

### Checklist operativa

1. Aggiorna versioni:
   - Spark -> `3.5.x`
   - Scala -> `2.12.x`
   - `scala.compat.version` -> `2.12`
2. Aggiorna artifact Spark con suffisso `_2.12`.
3. Aggiorna librerie test/plugin build.
4. Verifica dipendenza tra moduli (`rollback` e `delete-backup` dipendono da `repartition`).

### Errori tipici da principiante

- migrare solo il modulo repartition e dimenticare rollback/delete-backup;
- lasciare dipendenze `_2.11`.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Garantire stessa logica di ottimizzazione e stesso livello di integrità dati su Spark 3.

(Riferimento: driver e utility nei 3 moduli)

### Dove intervenire prima

1. `partition-optimization-repartition/.../Driver.scala`
2. `partition-optimization-repartition/.../FunctionUtility.scala`
3. Driver rollback e delete-backup

### Cosa cambiare (pratico)

- verificare semantica `exceptAll` nel check integrità;
- verificare `mergeSchema` e lettura parquet con Spark 3;
- validare move/delete su HDFS;
- gestire cast e null in modo esplicito se emergono differenze.

### Config transitoria utile

- eventuali `spark.sql.legacy.*` solo come ponte temporaneo.

### Errori tipici da principiante

- testare solo il path “happy path” senza rollback;
- cancellare backup prima della validazione integrità.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Mantenere il comportamento operativo su CDP 7.1.9 in sicurezza.

(Riferimento: `run_optimize_partition.sh`, `run_optimize_rollback.sh`, `run_optimize_delete_backup.sh`, `profiles/*/config.properties`, `deploy/params.properties`)

### Cosa verificare

1. sostituzione `spark2-submit` con submit Spark3;
2. conf executors/memory e parametri SQL;
3. correttezza path `root.path.files` e `path.properties`;
4. invocazione `msck_repair_table.sh` nel punto giusto.

### Allineamenti da onboarding CDP 7.1.9

- YARN: ticket Kerberos (`kinit -kt`) e cleanup al termine;
- CDE: usare `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE`;
- in CDE evitare filesystem locale/NFS per i dati;
- passare file config con `--files`;
- non usare conf non supportate CDE (es. `spark.shuffle.service.enabled=true`).

### Errori tipici da principiante

- path backup/originali invertiti;
- repair metadata non eseguito dopo riscrittura.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra `pom` root + moduli.
2. Migra e valida repartition.
3. Testa rollback su dataset controllato.
4. Testa delete-backup.
5. Esegui ciclo completo su tabella reale campione.
6. Promuovi su wave successive.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- test utility di calcolo partizioni;
- test check integrità (`count`, mismatch);
- test presenti (`Drivertest.scala` dove disponibile).

## 4.2 Integration test - test end-to-end

- ciclo completo: repartition -> rollback -> delete-backup;
- verifica:
  - row count pre/post
  - mismatch `exceptAll`
  - consistenza metadati Hive (`msck repair`)

(Riferimento: script deploy dei tre moduli)

## 4.3 Test non funzionali

- riduzione numero file e impatto performance query;
- tempi job su tabelle grandi;
- stabilità su run ripetute.

## 4.4 Criteri di accettazione finali

1. Nessuna perdita dati
2. Integrità verificata su tabelle campione
3. Rollback funzionante
4. Backup eliminato solo dopo esito positivo
5. Esecuzione stabile su Spark 3

## 5. Glossario minimo (per orientarti subito)

- **Repartition**: ridistribuzione dati in un numero ottimale di partizioni.
- **Rollback**: ripristino dello stato precedente.
- **Backup path**: copia di sicurezza (`_backup`) dei dati originali.
- **MSCK REPAIR TABLE**: riallineamento metadati partizioni in Hive.
- **Idempotenza**: riesecuzione senza effetti collaterali indesiderati.
