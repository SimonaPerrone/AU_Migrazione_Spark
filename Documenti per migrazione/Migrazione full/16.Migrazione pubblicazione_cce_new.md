# Migrazione Spark 2 -> Spark 3 - pubblicazione_cce

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`pubblicazione_cce` pubblica i risultati CCE per processi diversi (`P`, `PR`, `PEIN`, `PREIN`, `CA`), leggendo dati calcolati e producendo output/esiti.  
Il lancio è batch via script Spark con supporto import richieste, export esiti e refresh metadata.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark 2.4 e Scala 2.11;
- ha entrypoint `it.eng.au.pubblicazione_cce.Driver`;
- usa parsing args (`-p`, `-d`, `-f`) e dispatch su flow specifici.

(Riferimenti: `Documenti per migrazione/16.Migrazione pubblicazione_cce.md`, `pubblicazione_cce/pom.xml`, `Driver.scala`, `args/ArgsFactory.scala`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: legge properties path, data richieste, tipo flow.
- **`driver`**: crea contesto Spark e seleziona il processo da eseguire.
- **`factory`**: non presente come package centrale.
- **`flow`**: `PubblicazioneFlow` e `PubblicazioneCAFlow` (+ subflow ammissibilità/consumi).
- **`model`**: package `model` per strutture dati di processo.
- **`dao/controller/utility`**: DAO CCE, utility ambiente/log/file, schema.

(Riferimenti: `src/main/scala/it/eng/au/pubblicazione_cce/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `pubblicazione_cce/pom.xml`, `deploy/runSpark.sh`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Lo script `runSpark.sh` lancia `it.eng.au.pubblicazione_cce.Driver`.

### Step 2 - Lettura parametri e config

`ArgsFactory` valida flow e data; default data = giorno precedente.

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate(...)` apre il contesto Spark col nome job+flow.

### Step 4 - Lettura input

Il flow legge tabelle input CCE (calcolo/anagrafica/trattamento/track) e richieste.

### Step 5 - Pulizia e normalizzazione

Normalizza dati richieste/esiti prima della pubblicazione.

### Step 6 - Regole di business (flow)

Dispatch su processo:
- `P`, `PR`, `PEIN`, `PREIN` -> `PubblicazioneFlow`
- `CA` -> `PubblicazioneCAFlow`

### Step 7 - Costruzione dataset finale

Costruzione output pubblicazione e dataset esiti/export.

### Step 8 - Scrittura output

Scrittura tabelle output (es. esiti, filtri, output CA) + script supporto export/refresh.

### Step 9 - Chiusura e logging

Log finale e cleanup eventuale temporanei.

(Riferimenti base del flusso: `Driver.scala`, `args/ArgsFactory.scala`, `flow/*`, `deploy/*`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare il progetto a Spark3 mantenendo stabile la pubblicazione multi-flow.

(Riferimento: `pubblicazione_cce/pom.xml`)

### Checklist operativa

1. Aggiorna `spark-*` a `3.5.x`.
2. Aggiorna Scala a `2.12.x` e artifact `_2.12`.
3. Aggiorna librerie test/plugin build.
4. Verifica compatibilità `kryo-serializers` e dipendenze transitive.

### Errori tipici da principiante

- mismatch scala version / artifact suffix;
- plugin test legacy non compatibili;
- regressioni runtime su flow non testati.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Preservare il comportamento dei 5 flow di pubblicazione.

(Riferimento: `Driver.scala`, `flow/PubblicazioneFlow.scala`, `flow/PubblicazioneCAFlow.scala`)

### Dove intervenire prima

1. `Driver` (dispatch flow)
2. flow principali
3. DAO/schema output

### Cosa cambiare (pratico)

- verificare cast/date/null handling su Spark3;
- verificare join/union e scritture output;
- mantenere validazione flow (`CA/P/PR/PEIN/PREIN`).

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` solo temporaneamente.

### Errori tipici da principiante

- testare solo un flow (es. P) e non gli altri;
- non verificare coerenza output esiti/export.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Garantire run stabile su CDP 7.1.9.

(Riferimento: `deploy/runSpark.sh`, `deploy/params.properties`, script `runPubblicazioni-*.sh`)

### Cosa verificare

1. sostituire `spark2-submit` con submit Spark3;
2. tuning executor/driver/shuffle/memoryOverhead;
3. path properties HDFS/local corretti;
4. integrazione script `importRichieste.sh`, `exportEsiti.sh`, `refresh_impala.sh`.

### Errori tipici da principiante

- aggiornare solo runSpark.sh e dimenticare wrapper script;
- conf risorse non allineate tra ambienti.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna dependency/build.
2. Migra Driver + flow core.
3. Migra DAO/schema.
4. Aggiorna script runtime.
5. Esegui test per tutti i flow.
6. Promuovi in QA/cluster.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing args e validazione flow;
- utility e trasformazioni isolate;
- regole date/null.

## 4.2 Integration test - test end-to-end

- run completo per `P`, `PR`, `PEIN`, `PREIN`, `CA`;
- confronto Spark2 vs Spark3 su row count/KPI/schema;
- verifica pipeline script import/publish/export.

(Riferimento: struttura flow e script deploy)

## 4.3 Test non funzionali

- performance per singolo flow;
- stabilità su run ripetute;
- idempotenza output.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline pubblicazione corrente)

## 5. Glossario minimo (per orientarti subito)

- **Flow**: variante di processo pubblicazione.
- **Dispatch**: selezione del flow in base input.
- **DAO**: accesso dati input/output.
- **Schema**: definizione colonne/tipi.
- **Idempotenza**: riesecuzione coerente.
- **Refresh metadati**: riallineamento layer query dopo scrittura dati.
