# Migrazione Spark 2 -> Spark 3 - pubblicazione_pcg

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`pubblicazione_pcg` è un job batch che legge i consumi giornalieri SBG, seleziona la partizione corretta per `annomese`/`executionid`, trasforma i dati nel formato PCG e genera file CSV di output per distributore (piva).  
In parallelo salva un log tecnico di pubblicazione su HDFS/Hive (tabella info log).

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- parte da stack legacy Spark `1.6.0-cdh5.14.2` + Scala `2.10.5`;
- ha entrypoint `Driver` con componenti `args`, `dao`, `controller`, `utility`;
- usa script deploy `spark-submit.sh` e profili `coll/prod` con path HDFS/NFS.

(Riferimenti: `Documenti per migrazione/3.Migrazione pubblicazione_pcg.md`, `pubblicazione_pcg/pom.xml`, `pubblicazione_pcg/src/main/resources/deploy/spark-submit/spark-submit.sh`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: legge i parametri di run (`offset mese`, `sbg type`, path input/output, numero righe CSV).
- **`driver`**: inizializza Spark, calcola `date.run`/`year.month`, avvia il processo.
- **`factory`**: non presente come package dedicato.
- **`flow`**: non presente come package dedicato; logica nel controller.
- **`model`**: non presente come package `model`; struttura dati gestita in `schema`.
- **`dao/controller/utility`**: DAO leggono/scrivono dati, controller applica trasformazioni e scrive CSV, utility gestisce Spark/data/file.

(Riferimenti: `src/main/scala/it/eng/au/pubblicazionePcg/{Driver.scala,args,controller,dao,schema,utility}`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `1.6.0-cdh5.14.2`
- Scala/Python: `Scala 2.10.5`
- Java: `8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x` (se Scala)
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `pubblicazione_pcg/pom.xml`, `Documenti per migrazione/Documento Onboarding Cloudera CDP 7.1.9 v1.9.md`, `src/main/resources/profiles/*/config.properties`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Lo script `deploy/spark-submit/spark-submit.sh` lancia la classe main `it.eng.au.pubblicazionePcg.Driver` con argomenti CLI.

### Step 2 - Lettura parametri e config

`ParseCLIArgs` valida parametri obbligatori (`-m -s -n -d -o -l -i`) e `SparkImplicit.initialize` li carica nelle `jobProperties`.

### Step 3 - Inizializzazione Spark

`SparkImplicit` crea `SparkConf`, `SparkContext` e `HiveContext` (legacy), configura alcune proprietà SQL e inizializza `FileSystem`.

### Step 4 - Lettura input

`DailyConsumptionDAO.readAnnoMesePartition`:
1. legge le partizioni disponibili della tabella consumi,
2. seleziona l’`executionid` più recente per `annomese`,
3. legge i record filtro `annomese + executionid`.

### Step 5 - Pulizia e normalizzazione

`PubblicazionePCG.importMisure` mappa e rinomina colonne verso schema SBG misure, aggiunge metadati (`sessione`, `annomese`, `date.run`) e scrive parquet partizionato.

### Step 6 - Regole di business (flow)

`PubblicazionePCG.prepareDataFrame`:
- filtra i record (`trattamento = G`),
- applica pivot giornaliero `PRELIEVO_GIORN_*`,
- aggiunge colonne mancanti,
- sostituisce null con stringa vuota,
- distribuisce i record per piva e contatore CSV.

### Step 7 - Costruzione dataset finale

`RunnableAggregator` prepara i blocchi output (`ListMap key/counter + row`) e il naming file finale con timestamp.

### Step 8 - Scrittura output

`writeCsv` genera i CSV nel path output isilon e `writeInfoIntoTable` scrive il log pubblicazione in parquet partizionato su HDFS.

### Step 9 - Chiusura e logging

Il driver logga fine processo; eventuali errori in parsing/lettura/scrittura interrompono la run.

(Riferimenti base del flusso: `Driver.scala`, `controller/PubblicazionePCG.scala`, `controller/RunnableAggregator.scala`, `dao/sbg/DailyConsumptionDAO.scala`, `utility/SparkImplicit.scala`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare il progetto a Spark 3 + stack compatibile.

(Riferimento: `pubblicazione_pcg/pom.xml`)

### Checklist operativa

1. Aggiorna versioni:
   - `spark.version` -> `3.5.x`
   - `scala.version` -> `2.12.x` (se Scala)
   - `scala.minor.version` / `scala.compat.version` -> `2.12`
2. Aggiorna artifact Spark (`spark-core`, `spark-sql`, `spark-hive`) con suffisso corretto.
3. Aggiorna librerie compatibili Spark 3 (`spark-xml`, ecc.) se usate.
4. Rimuovi librerie obsolete (es. `spark-csv` legacy).
5. Aggiorna librerie test (ScalaTest/JUnit/specs2) e plugin build.
6. Verifica packaging/shading.

### Errori tipici da principiante

- lasciare dipendenze `_2.10`/`_2.11`;
- aggiornare Spark ma non plugin test/build;
- ignorare conflitti transitive dependency.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Rendere il codice compatibile con Spark 3.

(Riferimento: `Driver.scala`, `utility/SparkImplicit.scala`, `controller/*.scala`, `dao/sbg/*.scala`)

### Dove intervenire prima

1. `utility/SparkImplicit.scala` (migrazione da `SparkContext + HiveContext` a `SparkSession`).
2. `dao/sbg/DailyConsumptionDAO.scala` (SHOW PARTITIONS, filtri, lettura tabella).
3. `controller/PubblicazionePCG.scala` e `RunnableAggregator.scala` (pivot, repartition, write CSV/parquet).

### Cosa cambiare (pratico)

- Cast espliciti e gestione tipi.
- Date/Timestamp con format espliciti.
- Null handling in join/filtri.
- Allineamento schema prima di union/join.
- Verifica UDF e serializzazione.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` (solo ponte, poi rimuovere)
- eventuali altre `spark.sql.legacy.*`

### Errori tipici da principiante

- tenere `HiveContext` legacy senza refactor;
- non confrontare il comportamento di `SHOW PARTITIONS` e parsing `executionid` su Spark3.

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Far girare correttamente il job su cluster Spark 3.

(Riferimento: onboarding CDP 7.1.9 + `deploy/spark-submit/spark-submit.sh`, `profiles/coll|prod/config.properties`)

### Cosa verificare

1. Script `spark-submit` (class, jar, conf, risorse).
2. Parametri SQL (`spark.sql.adaptive.enabled`, `spark.sql.shuffle.partitions`, ecc.).
3. Compatibilità Hive Metastore/runtime target.
4. Path e permessi input/output/warehouse.

### Adeguamenti specifici onboarding CDP 7.1.9

- sostituire submit legacy con comando coerente target Spark3;
- se run su YARN: integrare autenticazione Kerberos (`kinit -kt`, cache ticket, cleanup);
- se run su CDE: usare `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE=spark35-test`;
- in CDE non usare filesystem locale/NFS per dati (config via `--files`, dati su HDFS/object storage);
- evitare `spark.shuffle.service.enabled=true` in CDE (non supportato).

### Errori tipici da principiante

- migrare codice ma lasciare `spark-submit` legacy;
- path `/mnt/...` non accessibili in CDE;
- conf duplicate/errate nello script (es. doppio `spark.driver.extraJavaOptions`).

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna build/dependency.
2. Porta a compilazione pulita.
3. Correggi codice impattato.
4. Aggiorna config runtime/submit.
5. Esegui test locali/integrati.
6. Promuovi in QA/cluster.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing args/config
- utility e trasformazioni isolate
- null/date/decimal/cast

## 4.2 Integration test - test end-to-end

- pipeline completa su dataset campione
- confronto Spark2 vs Spark3:
  - row count
  - chiavi business
  - KPI/aggregati
- verifica schema output (nomi/tipi/partizioni)

(Riferimento: `Driver.scala`, `PubblicazionePCG.scala`, `RunnableAggregator.scala`, `DailyConsumptionDAO.scala`)

## 4.3 Test non funzionali

- performance (tempo/memoria)
- stabilità run ripetute
- idempotenza/recovery

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline del documento attuale + onboarding CDP 7.1.9)

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: oggetto principale per usare Spark SQL/DataFrame.
- **DAO**: componente che legge/scrive dati da/verso sorgenti.
- **Flow**: sequenza di trasformazioni business.
- **Schema**: struttura colonne + tipi di un dataset.
- **Idempotenza**: rieseguire il job senza effetti collaterali non voluti.
