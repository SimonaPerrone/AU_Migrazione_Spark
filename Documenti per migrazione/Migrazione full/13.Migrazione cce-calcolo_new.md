# Migrazione Spark 2 -> Spark 3 - cce-calcolo

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`cce-calcolo` è un job batch Spark per il calcolo CCE su più modalità (`P`, `PR`, `Pein`, `PRein`) con ramo massivo/incrementale.  
Legge dati da flussi misure + RCU/RCUS + report ammissibilità, esegue annullamenti e calcoli, e scrive output/tracking su tabelle Hive CCE.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8;
- ha entrypoint `it.eng.au.cceCalcolo.Driver`;
- usa `ArgsFactory` con argomenti business (`-a -m -t -f`);
- ha script deploy `run_cce.sh` con tuning risorse e conf Spark SQL.

(Riferimenti: `Documenti per migrazione/13.Migrazione cce-calcolo.md`, `cce-calcolo/pom.xml`, `src/main/resources/deploy/run_cce.sh`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parser parametri run (anno/mese/tipo/massivo).
- **`driver`**: orchestra tutta la pipeline (letture, branch calcolo, scritture finali).
- **`factory`**: non presente come package dedicato.
- **`flow`**: controller:
  - `AmmissibilitaCheckController`
  - `AnnullamentoMisureController`
  - `CalcoloController`
- **`model`**: modelli business/tracking (`CceCalcTrackModel`).
- **`dao/controller/utility`**: DAO per input/output Hive, utility env/log, schema per domini.

(Riferimenti: `src/main/scala/it/eng/au/cceCalcolo/{Driver.scala,args/*,controller/*,dao/*,schema/*,utility/*}`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x` (raccomandato `3.5.x`)
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `cce-calcolo/pom.xml`, `run_cce.sh`, `deploy/conf/application.conf`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

`run_cce.sh` raccoglie parametri (`-a -m -t -f`) e runtime Spark (cores/memory/executors), poi lancia `spark2-submit` su `it.eng.au.cceCalcolo.Driver`.

### Step 2 - Lettura parametri e config

`ArgsFactory` valida:
- `tipoCalc` in `{P, PR, Pein, PRein}`
- obbligo `massivoFlag` per `PR/PRein`  
Carica inoltre config da `application.conf` / profiles.

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate(APPLICATION_NAME, LOG_NAME)` inizializza Spark e contesto logging.

### Step 4 - Lettura input

Il Driver istanzia e legge molti DAO:
- anagrafiche RCU/RCUS
- flussi misure quarti/estensione (inclusi `*_in`)
- report ammissibilità
- ghigliottina
- calc track storico

### Step 5 - Pulizia e normalizzazione

`AmmissibilitaCheckController` unisce report pod/file e produce dataset ammissibilità.

### Step 6 - Regole di business (flow)

In base a `(tipoCalc, massivoFlag, meseCalc)` esegue i branch:
- `P` -> annullamenti + calcolo P
- `PR` -> massivo o incrementale
- `Pein` -> branch EIN
- `PRein` -> massivo o incrementale EIN  
Con scrittura di `cceCalcTrack` per esito run.

### Step 7 - Costruzione dataset finale

Produce dataset output di:
- annullamenti (`1g/2g`, `1gEin/2gEin`)
- calcolo (`P`, `PR`, `Pein`, `PRein`)
- anagrafica e trattamento

### Step 8 - Scrittura output

DAO output scrivono in Hive le tabelle CCE (`cce_calcolo_*`, `cce_mo_annullate_*`, `cce_calc_track`).

### Step 9 - Chiusura e logging

`LogUtility.printInitialLog/printFinalLog` e log error handling nel Driver.

(Riferimenti base del flusso: `Driver.scala`, `args/ArgsFactory.scala`, `controller/*`, `deploy/conf/application.conf`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare il progetto a Spark 3 + Scala 2.12 mantenendo i branch business invariati.

(Riferimento: `cce-calcolo/pom.xml`)

### Checklist operativa

1. Aggiorna versioni:
   - Spark -> `3.5.x`
   - `scala.version` -> `2.12.x`
   - `scala.compat.version` -> `2.12`
2. Aggiorna artifact Spark (`core/sql/hive`) in `_2.12`.
3. Aggiorna librerie test/plugin build.
4. Verifica compatibilità dipendenze transitive.

### Errori tipici da principiante

- build compilata ma test rotti per mismatch Scala;
- lasciare librerie legacy non compatibili;
- dimenticare artifact `spark-hive` coerente.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Garantire equivalenza funzionale su tutti i branch (`P`, `PR`, `Pein`, `PRein`).

(Riferimento: `Driver.scala`, controller/DAO)

### Dove intervenire prima

1. `Driver.scala` (pattern match dei branch)
2. controller di calcolo/annullamento/ammissibilità
3. DAO e schema output Hive

### Cosa cambiare (pratico)

- verificare cast/date/timestamp e null handling;
- verificare `unionByName` e coerenza schema;
- verificare join e filtri con semantica Spark3;
- validare scrittura output e tracking invariati.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` (solo ponte, poi rimozione).

### Errori tipici da principiante

- testare solo `P` e non gli altri rami;
- non validare ramo incrementale vs massivo.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire in sicurezza il job su CDP 7.1.9.

(Riferimento: `run_cce.sh`, `profiles/{prod,dev,coll}/config.properties`, `deploy/conf/application.conf`)

### Cosa verificare

1. Sostituire `spark2-submit` con submit Spark3.
2. Ricontrollare conf:
   - dynamic allocation
   - `spark.sql.shuffle.partitions`
   - `spark.sql.sources.partitionOverwriteMode=dynamic`
3. Path `deploy.path`, log path, HDFS tables/path.
4. Compatibilità conf submit per cluster target.

### Errori tipici da principiante

- mantenere tuning Spark2 non adatto a Spark3;
- mismatch tra config profilo e script;
- ignorare gestione credenziali/kerberos.

### Allineamenti onboarding CDP 7.1.9

- YARN: `kinit -kt` + cleanup ticket;
- CDE: `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE`;
- in CDE evitare filesystem locale/NFS per dati;
- distribuire file config con `--files`;
- non usare conf non supportate in CDE.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra `pom.xml` e build.
2. Migra/valida Driver + Args.
3. Migra controller/DAO per rami `P` e `PR`.
4. Migra rami `Pein` e `PRein`.
5. Aggiorna script deploy.
6. Esegui regressione completa multi-ramo.

## 5. Glossario minimo (per orientarti subito)

- **Massivo**: ricalcolo completo per perimetro ampio.
- **Incrementale**: ricalcolo parziale su delta.
- **Ammissibilità**: filtro record validi per il calcolo.
- **Annullamento misure**: rimozione/neutralizzazione misure non valide.
- **Calc track**: storico tecnico degli esiti di calcolo.
