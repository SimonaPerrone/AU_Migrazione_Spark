# Migrazione Spark 2 -> Spark 3 - ingestion-elettrico-ammissibilita

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`ingestion-elettrico-ammissibilita` valida i flussi elettrici (EE/SMIS) a due livelli:
1. ammissibilità file
2. ammissibilità POD

Esegue anche un controllo preliminare di aggiornamento tabelle RCU/RCUGAS.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8;
- entrypoint `it.eng.au.ammissibilita.CheckAmmissibilitaDriver`;
- esegue `CheckAmmissibilitaFile.run` e poi `CheckAmmissibilitaPod.run`;
- ha script `deploy/bin/flusso-misure-ammissibilita.sh`;
- include jar esterni in deploy (`ImpalaJDBC41.jar`, `ojdbc7-12.7.0.jar`).

(Riferimenti: `Documenti per migrazione/29.Migrazione ingestion-elettrico-ammissibilita.md`, sorgenti progetto)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parametri di run (1G/2G/SMIS, giorno/mese/anno).
- **`driver`**: coordina pre-check Sqoop + validazione file + validazione POD.
- **`factory`**: non centrale.
- **`flow`**: flusso sequenziale file -> pod.
- **`model`**: metadata XML e messaggi di esito.
- **`dao/controller/utility`**: letture RCU/RCUGAS e funzioni di check.

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9

## 2. Funzionamento step by step

### Step 1 - Avvio job

`flusso-misure-ammissibilita.sh` lancia `CheckAmmissibilitaDriver`.

### Step 2 - Lettura parametri e config

Parse opzioni (EE/SMIS, finestra giorno).

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate("Ammissibilità EE/SMIS")`.

### Step 4 - Lettura input

Legge cartelle XML e tabelle RCU/RCUGAS.

### Step 5 - Pulizia e normalizzazione

Selezione file validi per naming/pattern e normalizzazione metadata.

### Step 6 - Regole di business (flow)

- check aggiornamento Sqoop;
- validazione file;
- validazione POD sui file ammessi.

### Step 7 - Costruzione dataset finale

Creazione report esiti file e POD.

### Step 8 - Scrittura output

Scrittura report e log su Hive/path output.

### Step 9 - Chiusura e logging

Log finale; in errore interrompe processo.

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Migrare mantenendo invariata la catena di validazione.

### Checklist operativa

1. Spark -> `3.5.x`
2. Scala -> `2.12.x`
3. artifact `_2.12`
4. aggiornare plugin/test.

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Conservare equivalenza su regole file/POD.

### Dove intervenire prima

1. `CheckAmmissibilitaDriver`;
2. `CheckAmmissibilitaFile`;
3. `CheckAmmissibilitaPod`.

### Cosa cambiare (pratico)

- gestione date/parser XML;
- null handling e cast dataframe;
- compatibilità funzioni Spark SQL usate nei report.

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Esecuzione corretta su CDP/CDE.

### Cosa verificare

1. `spark2-submit` -> submit Spark3;
2. path conf (`application.conf`, `log4j.properties`) via `--files`;
3. attenzione a dipendenze JDBC esterne;
4. Kerberos valido su YARN;
5. su CDE evitare dipendenze da fs locale non distribuito.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra pom.
2. Migra driver.
3. Migra file validation.
4. Migra pod validation.
5. Aggiorna script deploy/bin.
6. Esegui test EE e SMIS.

## 5. Glossario minimo (per orientarti subito)

- **Ammissibilità file**: controllo struttura e metadati file.
- **Ammissibilità POD**: controllo semantico sui punti di prelievo.
- **Sqoop check**: verifica aggiornamento dati sorgente.
- **SMIS**: variante flusso con regole dedicate.
- **XML metadata**: informazioni estratte dal file XML.
- **Idempotenza**: risultato coerente ai rilanci.
