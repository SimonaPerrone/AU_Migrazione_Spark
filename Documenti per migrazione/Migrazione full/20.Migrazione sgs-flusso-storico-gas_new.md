# Migrazione Spark 2 -> Spark 3 - sgs-flusso-storico-gas

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`sgs-flusso-storico-gas` realizza il flusso storico gas in tre fasi:
1. **Perimetro**
2. **Aggregazione**
3. **Pubblicazione**

Le fasi sono orchestrate da workflow shell e condividono execution track e configurazioni comuni.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark 2.4 + Scala 2.11;
- ha driver distinti per `run/perimetro`, `run/aggregazione`, `run/pubblicazione`;
- ha orchestrazione sequenziale con `run_sgs_workflow.sh`.

(Riferimenti: `Documenti per migrazione/20.Migrazione sgs-flusso-storico-gas.md`, `sgs-flusso-storico-gas/pom.xml`, `run_sgs_workflow.sh`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parse path properties per i run.
- **`driver`**: tre driver separati (perimetro/aggregazione/pubblicazione).
- **`factory`**: non centrale; controller orchestrano i rami.
- **`flow`**: run package diviso per fase.
- **`model`**: model execution/report nei package dedicati.
- **`dao/controller/utility`**: presenti e ampi per tutte le fasi.

(Riferimenti: `src/main/scala/it/eng/au/sgsFlussoStoricoGas/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `sgs-flusso-storico-gas/pom.xml`, `deploy/run_sgs_*.sh`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

`run_sgs_workflow.sh` esegue in sequenza:
- `run_sgs_perimetro.sh`
- `run_sgs_aggregazione.sh`
- `run_sgs_pubblicazione.sh`

### Step 2 - Lettura parametri e config

Ogni step usa `params.properties` + profilo ambiente.

### Step 3 - Inizializzazione Spark

Ogni script lancia `spark2-submit` sul driver della fase corrispondente.

### Step 4 - Lettura input

- perimetro: raw sqoop + tabelle RCUGAS;
- aggregazione: consumi + perimetri + anagrafiche;
- pubblicazione: aggregati validati e regole di pubblicazione.

### Step 5 - Pulizia e normalizzazione

Filtri per giorno esecuzione e flag booleani di attivazione perimetro/aggregazione/pubblicazione.

### Step 6 - Regole di business (flow)

Controller di fase applicano calcoli specifici (SWG/UIG/VTG, UDB/UDD, prevalidation, validazione pubblicazione).

### Step 7 - Costruzione dataset finale

Ogni fase produce dataset propri + aggiornamento execution track.

### Step 8 - Scrittura output

Scrittura su path/tabelle SGS (perimetri, aggregatore info, pubblicazione info, report).

### Step 9 - Chiusura e logging

Workflow interrompe catena al primo errore e logga esito complessivo.

(Riferimenti base del flusso: `run/*/Driver.scala`, `deploy/run_sgs_*.sh`, `deploy/params.properties`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Migrare il progetto mantenendo intatta la catena a 3 step.

(Riferimento: `sgs-flusso-storico-gas/pom.xml`)

### Checklist operativa

1. Spark -> `3.5.x`
2. Scala -> `2.12.x` + artifact `_2.12`
3. Aggiorna plugin/test libs.
4. Verifica librerie transitive (`kryo`, `scopt`, ecc.).

### Errori tipici da principiante

- migrare solo il codice e non workflow script;
- incompatibilità scala nei test;
- non controllare comportamento execution track.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Confermare equivalenza funzionale di perimetro/aggregazione/pubblicazione.

(Riferimento: `run/perimetro/Driver.scala`, `run/aggregazione/Driver.scala`, `run/pubblicazione/Driver.scala`)

### Dove intervenire prima

1. run perimetro
2. run aggregazione
3. run pubblicazione

### Cosa cambiare (pratico)

- verificare `unionByName`, cast/date/null;
- verificare logica flag attivazione per giorno;
- verificare query/scritture parquet e tabelle.

### Config transitoria utile

- eventuali `spark.sql.legacy.*` solo in fase ponte.

### Errori tipici da principiante

- non testare combinazioni flag booleani;
- non verificare run con step intermedi disattivati.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Far girare i 3 step su CDP 7.1.9 in modo robusto.

(Riferimento: `deploy/run_sgs_perimetro.sh`, `run_sgs_aggregazione.sh`, `run_sgs_pubblicazione.sh`, `profiles/prod/config.properties`)

### Cosa verificare

1. migrazione submit Spark3 per tutti e 3 gli script;
2. conf risorse per fase (perimetro più leggero, agg/pub più pesanti);
3. path deploy/HDFS/XML/XSD;
4. regole di activation day e flag fase.

### Errori tipici da principiante

- aggiornare solo uno script su tre;
- conf incoerenti tra workflow e step;
- path xml/xsd non allineati.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna build.
2. Migra perimetro.
3. Migra aggregazione.
4. Migra pubblicazione.
5. Aggiorna workflow/script.
6. Testa catena completa.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- utility args/config;
- controller fase;
- regole filtraggio/normalizzazione.

## 4.2 Integration test - test end-to-end

- run singolo per fase;
- run workflow completo P -> A -> Pub;
- confronto Spark2 vs Spark3 su KPI e schema output.

(Riferimento: package `run/*`, `controller/*`, `dao/*`)

## 4.3 Test non funzionali

- performance su dati reali;
- stabilità e restartability;
- idempotenza run multipli.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline SGS attuale)

## 5. Glossario minimo (per orientarti subito)

- **Perimetro**: selezione/normalizzazione dominio dati.
- **Aggregazione**: consolidamento consumi per entità target.
- **Pubblicazione**: produzione output finali distribuiti.
- **Execution track**: tracciatura esecuzioni e competenze.
- **Flag attivazione**: switch per abilitare/disabilitare rami.
- **Idempotenza**: riesecuzione coerente.
