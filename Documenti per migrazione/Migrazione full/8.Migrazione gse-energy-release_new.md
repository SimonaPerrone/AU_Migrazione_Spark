# Migrazione Spark 2 -> Spark 3 - gse-energy-release

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`gse-energy-release` è una pipeline batch multi-modulo che produce risultati energetici GSE in due varianti:
- **calcolo mensile** (`gse-calcolo-mensile`)
- **calcolo annuale** (`gse-calcolo-annuale`)

Il flusso operativo standard è: **import Sqoop** (perimetro/richieste) -> **elaborazione Spark** -> **export Sqoop** dei risultati.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è un Maven multi-modulo (`common-module`, `gse-calcolo-mensile`, `gse-calcolo-annuale`);
- usa stack Spark 2.4 + Scala 2.11;
- usa script deploy dedicati per mensile e annuale.

(Riferimenti: `Documenti per migrazione/8.Migrazione gse-energy-release.md`, `gse-energy-release/pom.xml`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: legge i parametri di avvio (`-p` properties path).
- **`driver`**: coordina il run (main + chiamata a `run()`).
- **`factory`**: non presente come package dedicato (la logica è in controller/dao comuni).
- **`flow`**: `Prepare` + `Transform` + controller comuni di consumo.
- **`model`**: schema e dataset gestiti nei package `schema`.
- **`dao/controller/utility`**: lettura/scrittura tabelle + log + environment.

(Riferimenti:  
`gse-calcolo-mensile/src/main/scala/.../Driver.scala`,  
`gse-calcolo-annuale/src/main/scala/.../Driver.scala`,  
`common-module/src/main/scala/it/eng/au/gse/common/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven` (multi-modulo)

Target:

- Spark: `3.x` (raccomandato `3.5.x`)
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `gse-energy-release/pom.xml`, `common-module/pom.xml`, `gse-calcolo-*/pom.xml`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Si lancia `run-gse-energy-release-calcolo-mensile.sh` o `run-gse-energy-release-calcolo-annuale.sh`.

### Step 2 - Lettura parametri e config

Gli script leggono `-p` (default `${hdfs.deploy.path}/params.properties`) e risolvono `DEPLOY_PATH`.

### Step 3 - Inizializzazione Spark

Lo `spark-submit-gse-calcolo-*.sh` avvia il `Driver` modulo (`calcoloMensile.Driver` / `calcoloAnnuale.Driver`) con conf executors/memory.

### Step 4 - Lettura input

Nel codice vengono letti:
- richieste (`GseRichiesteMensiliDao` / `GseRichiesteAnnualiDao`)
- perimetro (`GsePerimetroDao`)
- consumi DWH (`DwhConsumiDao`)

### Step 5 - Pulizia e normalizzazione

`Prepare.prepare*` e `PrepareCommon.prepareDwhConsumi` puliscono e allineano i dataset per i join.

### Step 6 - Regole di business (flow)

`Transform.joinPerimeterAndRequests` + `TransformCommon.joinDwhConsumiWithPods` + `ConsumptionController.computeMonthlyConsumptions`.

### Step 7 - Costruzione dataset finale

Produzione del risultato aggregato:
- mensile: `gseAggrM`
- annuale: `gseAggrA`

### Step 8 - Scrittura output

DAO finali scrivono tabelle target ed export (`write` + `writeExport`), poi lo script fa Sqoop export verso valle.

### Step 9 - Chiusura e logging

`LogUtility.printInitialLog/printFinalLog` + log script (sqoop/spark).

(Riferimenti base del flusso:  
`gse-calcolo-mensile/.../Driver.scala`, `gse-calcolo-annuale/.../Driver.scala`,  
`run-gse-energy-release-calcolo-*.sh`, `spark-submit-gse-calcolo-*.sh`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare tutto il progetto a Spark 3 + Scala 2.12 in modo coerente su parent e moduli.

(Riferimento: `gse-energy-release/pom.xml`, `common-module/pom.xml`, `gse-calcolo-mensile/pom.xml`, `gse-calcolo-annuale/pom.xml`)

### Checklist operativa

1. Aggiorna versioni:
   - `spark.version` (o versioni hardcoded Spark) -> `3.5.x`
   - `scala.version` -> `2.12.x`
   - `scala.compat.version` -> `2.12`
2. Aggiorna artifact Spark (`spark-core`, `spark-sql`, `spark-hive`) con suffisso `_2.12`.
3. Aggiorna librerie test (`scalatest/specs2/junit`) compatibili.
4. Verifica plugin build (`scala-maven-plugin`, `shade`, `surefire`) compatibili Java/Spark target.
5. Allinea dipendenze tra parent, common-module e moduli calcolo.

### Errori tipici da principiante

- aggiornare solo un modulo e lasciare parent/common non allineati;
- lasciare artifact Spark `_2.11`;
- non verificare dipendenze transitive.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Mantenere invariata la logica business su Spark 3.

(Riferimento: `Driver.scala`, `controller/*`, `dao/*` nei due moduli)

### Dove intervenire prima

1. `gse-calcolo-mensile/.../Driver.scala`
2. `gse-calcolo-annuale/.../Driver.scala`
3. controller `Prepare/Transform` (mensile+annuale) e `common-module`.

### Cosa cambiare (pratico)

- rendere espliciti cast/date/timestamp;
- verificare join e gestione null;
- controllare eventuali differenze SQL Spark 3 su funzioni/semantica;
- verificare schema finale di output prima di `writeExport`.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` solo temporaneamente (poi rimuovere).

### Errori tipici da principiante

- testare solo il job mensile e non quello annuale;
- non confrontare output business pre/post migrazione.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire stabilmente la pipeline end-to-end (sqoop + spark + sqoop) su CDP 7.1.9.

(Riferimento: `run-gse-energy-release-calcolo-*.sh`, `spark-submit-gse-calcolo-*.sh`, `profiles/prod/config.properties`, `deploy/params.properties`)

### Cosa verificare

1. Sostituire `spark2-submit` con submit Spark3 nel runtime target.
2. Parametri Spark SQL/allocazione:
   - `spark.sql.adaptive.enabled`
   - `spark.sql.shuffle.partitions`
   - `spark.executor.memoryOverhead`
3. Percorsi deploy/log e permessi HDFS.
4. Connessioni Sqoop/JDBC e credenziali.

### Allineamenti da onboarding CDP 7.1.9

- su YARN: aggiungere gestione Kerberos (`kinit -kt` prima del run e cleanup ticket cache);
- su CDE: usare `CDE_CREDENTIALS_FILE` e `CDE_CONFIG_PROFILE` (es. `spark35-test`);
- evitare accesso dati su filesystem locale/NFS in CDE;
- passare config necessari con `--files`;
- evitare conf non supportate in CDE (es. `spark.shuffle.service.enabled=true`).

### Errori tipici da principiante

- migrare il jar ma non gli script run/sqoop;
- non separare validazione mensile da annuale.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna parent + common-module + moduli calcolo.
2. Porta build/compilazione pulita.
3. Migra e valida codice mensile.
4. Migra e valida codice annuale.
5. Aggiorna script run/spark-submit/sqoop.
6. Esegui test end-to-end e confronto con baseline.

  - row count
  - chiavi business

- performance run mensile/annuale;

- verifica consumi risorse executor/driver.

## 4.4 Criteri di accettazione finali

1. Output equivalente al legacy (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Pipeline sqoop+spark+sqoop stabile
4. Stabilità su almeno 3 run consecutivi

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: oggetto principale per usare Spark SQL/DataFrame.
- **DAO**: componente che legge/scrive dati da tabelle/sorgenti.
- **Flow**: sequenza di trasformazioni business.
- **Schema**: struttura colonne + tipi del dataset.
- **Idempotenza**: riesecuzione senza effetti collaterali indesiderati.
