# MIGRAZIONE_SPARK3_EE_SWITCHING

## 1. Descrizione Progetto

### 1.1 Obiettivo e contesto
Il progetto `ee_switching` gestisce i flussi di switching elettrico su due macro-modalità:
- **flussi funzionali**
- **flussi storici**

L’elaborazione è orchestrata via Spark e script di deploy, con parametri di filtro su date, POD, distributori/UDD e timestamp.

### 1.2 Perimetro funzionale e tecnico
Il job:
1. riceve i parametri da riga comando/file;
2. seleziona il flow corretto;
3. esegue regole di filtraggio e trasformazione;
4. produce output dati/file per le pipeline successive.

Sono presenti anche script esterni per load/generazione file, con orchestrazione operativa su ambiente cluster.

### 1.3 Architettura logica
- **Entrypoint**: `it.au.misure.ee_switching.driver.FlowDriver`
- **Arg parsing/validazione**: `FlowArgsFactory`
- **Selezione flow**: `FlowFactory`
- **Flow applicativi**: `FunzionaliFlow`, `StoriciFlow`
- **Supporto**: package `factory`, `filterPod`, `utility`, `model`
- **Deploy**: set ampio di script in `src/main/resources/deploy` (load, file generation, HQL, Oozie, query).

### 1.4 Stack tecnologico attuale
- Spark `2.4.0.cloudera2`
- Scala `2.11.12`
- Java 8
- Maven + scala-maven-plugin + shade
- Dipendenze `spark-hive/spark-sql/spark-core`, `spark-xml`, `scopt`
- Test Scala presenti (`src/test/scala` su args/filter/flow/utility)

## 2. Funzionamento step by step del progetto

1. Viene lanciato `FlowDriver` con `--flow-name` e parametri opzionali.
2. `FlowArgsFactory` effettua parse, validazione semantica e lettura eventuali file input (date/list/pairs/timestamp).
3. `FlowFactory` risolve il flow richiesto.
4. Viene inizializzato il contesto Spark/Environment.
5. Il flow (`FunzionaliFlow` o `StoriciFlow`) esegue filtri e trasformazioni sul perimetro richiesto.
6. I risultati vengono salvati secondo la logica del flusso.
7. Gli script deploy (`ee-switching-load*.sh`, `ee-switching-file*.sh`, `spark-submit-*.sh`) gestiscono pipeline operative e pubblicazione.

3. Verifica compatibilità librerie (`spark-xml`, `scopt`, test libs).

1. Verifica compatibilità DataFrame API e SQL Spark 3 (cast/date/null/ANSI mode).
2. Validazione completa dei filtri temporali (run ordinaria vs run parametrica).
3. Verifica gestione eccezioni/validazioni input in `FlowArgsFactory`.

2. Verifica conf Spark non più valide o da ritoccare (dynamic allocation, memory overhead, shuffle).
3. Verifica script Oozie/query/HQL collegati alla nuova piattaforma.

### 3.4 Configurazioni e profili

2. Controllo coerenza parametri cluster/path HDFS.

## 4. Test da prevedere

### 4.1 Test unitari
1. Test parse/validazione argomenti (`FlowArgsFactory`) su combinazioni valide/non valide.
2. Test regole filtro POD/distributori/UDD/date.
3. Test logiche di flow funzionali/storici.

### 4.2 Test integrazione
1. Esecuzione end-to-end di run ordinaria.
2. Esecuzione run parametrica (timestamp/date/list).
3. Verifica output su dataset campione e allineamento con aspettative business.

### 4.3 Test regressione
1. Confronto output Spark 2 vs Spark 3 a parità input.
2. Verifica cardinalità/completezza per flussi funzionali e storici.
3. Verifica idempotenza su rilanci stessa finestra dati.

### 4.4 Test operativi
1. Dry-run script di deploy/load/generazione file.
2. Verifica gestione errori, log e restart.
3. Validazione schedulazioni/Oozie (se usate in esercizio).

## 5. Glossario minimo
- **Flusso funzionale**: elaborazione operativa corrente.
- **Flusso storico**: rielaborazione su perimetri temporali storici.
- **Run ordinaria**: esecuzione standard senza filtri avanzati.
- **Run parametrica**: esecuzione pilotata da date/list/timestamp.
