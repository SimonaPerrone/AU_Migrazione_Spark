# Migrazione Spark 2 -> Spark 3 - scambio-dati-gasivori

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`scambio-dati-gasivori` è un job batch che pubblica dati gasivori in modalità multiple (`CC`, `CSEA`, `ID`, `UDD`, `UDB`, `AMM`).  
Lo script esegue prima import Sqoop per le modalità richieste, poi avvia Spark che lancia in sequenza gli aggregatori.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark `2.4.0.cloudera2` + Scala `2.11.12`;
- ha entrypoint `it.eng.au.scambioDatiGasivori.Driver`;
- usa `ArgsFactory` e `AggregatorFactory` per governare i mode di esecuzione;
- ha script deploy/sqoop strutturati per modalità.

(Riferimenti: `Documenti per migrazione/11.Migrazione scambio-dati-gasivori.md`, `scambio-dati-gasivori/pom.xml`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parser CLI (`-p` properties, `-m` modes).
- **`driver`**: inizializza ambiente e lancia gli aggregatori.
- **`factory`**: mappa i mode (`CC,CSEA,...`) agli aggregatori concreti.
- **`flow`**: sequenza di aggregatori `run()` in base ai mode.
- **`model`**: schemi output in package `schema`.
- **`dao/controller/utility`**:
  - DAO per tabelle filiera/perimetro,
  - controller aggregatori (`CcAggregator`, `CseaAggregator`, `...`),
  - utility env/log/properties/file.

(Riferimenti:  
`src/main/scala/it/eng/au/scambioDatiGasivori/{Driver.scala,args/*,factory/*,controller/*,dao/*,schema/*,utility/*}`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x` (raccomandato `3.5.x`)
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `scambio-dati-gasivori/pom.xml`, script deploy)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Si lancia `run-pubblicazione-dati-gasivori.sh` con eventuali `-p` (properties) e `-m` (modes).

### Step 2 - Lettura parametri e config

Lo script valida i mode e legge path deploy/config da properties.

### Step 3 - Inizializzazione Spark

`spark-submit-pubblicazione-dati-gasivori.sh` avvia `Driver` con `-p` e `-m`.

### Step 4 - Lettura input

Prima del job Spark, lo script esegue Sqoop import per ogni mode selezionato (`CC`, `CSEA`, `ID`, `UDB`, `UDD`, `AMM`).

### Step 5 - Pulizia e normalizzazione

`Driver` imposta proprietà runtime (`daterun`, `output.file.modes`) e setup ambiente.

### Step 6 - Regole di business (flow)

`AggregatorFactory.getAggregators` costruisce la lista aggregatori; il Driver esegue `agg.run()` in sequenza.

### Step 7 - Costruzione dataset finale

Ogni aggregatore produce il proprio output (file/tabelle) secondo lo schema del mode.

### Step 8 - Scrittura output

Scrittura output filiera + info log; a fine script viene fatta pulizia delle cartelle temporanee.

### Step 9 - Chiusura e logging

Log iniziale/finale e log per singolo aggregatore/modo.

(Riferimenti base del flusso:  
`Driver.scala`, `ArgsFactory.scala`, `AggregatorFactory.scala`,  
`run-pubblicazione-dati-gasivori.sh`, `spark-submit-pubblicazione-dati-gasivori.sh`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Aggiornare build e dipendenze a Spark 3 + Scala 2.12.

(Riferimento: `scambio-dati-gasivori/pom.xml`)

### Checklist operativa

1. Aggiorna versioni Spark/Scala:
   - Spark -> `3.5.x`
   - `scala.version` -> `2.12.x`
   - `scala.compat.version` -> `2.12`
2. Aggiorna artifact Spark `_2.12`.
3. Aggiorna scopt/scalatest/plugin build a versioni compatibili.
4. Verifica packaging jar con `shade`.

### Errori tipici da principiante

- dimenticare l’allineamento tra `scala.version` e artifact `_2.xx`;
- aggiornare Spark senza verificare librerie CLI/test.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Mantenere corretta la catena aggregatori e il contenuto output per ogni mode.

(Riferimento: `Driver.scala`, `factory/AggregatorFactory.scala`, `controller/*.scala`, `dao/*.scala`)

### Dove intervenire prima

1. `Driver.scala`
2. `AggregatorFactory.scala`
3. aggregatori e DAO più usati (CC/CSEA/ID/UDB/UDD/AMM)

### Cosa cambiare (pratico)

- verificare cast/date/null nei DataFrame;
- validare schema output per ciascun mode;
- controllare eventuali join/union con semantica differente Spark3;
- garantire che i mode invalidi continuino a generare errore esplicito.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` solo se necessario e solo temporaneamente.

### Errori tipici da principiante

- testare un solo mode e dichiarare finita la migrazione;
- non confrontare output file e row count per ogni aggregatore.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire stabilmente run Sqoop + Spark su CDP 7.1.9.

(Riferimento: deploy script + profiles)

### Cosa verificare

1. sostituzione `spark2-submit` con submit Spark3;
2. conf risorse (`num-executors`, memory, dynamic allocation);
3. path deploy/log/properties e permessi;
4. script Sqoop per tutte le modalità.

### Allineamenti da onboarding CDP 7.1.9

- su YARN: Kerberos (`kinit -kt` + cleanup ticket cache);
- su CDE: usare `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE`;
- in CDE evitare dipendenza da filesystem locale/NFS per dati applicativi;
- passare file config con `--files`;
- attenzione a opzioni Sqoop non supportate/critiche (es. `--direct` quando non compatibile).

### Errori tipici da principiante

- script Spark migrato ma script Sqoop no;
- configurazioni diverse tra `prod` e `test` non riallineate.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna `pom.xml` e build.
2. Migra `Driver` + `AggregatorFactory`.
3. Migra aggregatori principali (uno per volta).
4. Aggiorna script deploy/sqoop.
5. Testa tutti i mode.
6. Confronta con baseline e promuovi.

## 4.4 Criteri di accettazione finali

1. Output equivalente al legacy per ogni mode
2. Nessun errore runtime Spark 3
3. Script Sqoop + Spark stabili
4. Pulizia temporanei senza effetti collaterali

## 5. Glossario minimo (per orientarti subito)

- **Mode**: variante di esecuzione (CC/CSEA/ID/UDD/UDB/AMM).
- **Aggregator**: componente che implementa una specifica trasformazione/output.
- **Factory**: componente che seleziona cosa eseguire in base ai mode.
- **DAO**: accesso a dati sorgente/target.
- **Pipeline**: sequenza Sqoop import -> Spark aggregazioni -> output.
- **Idempotenza**: riesecuzione senza risultati incoerenti.
