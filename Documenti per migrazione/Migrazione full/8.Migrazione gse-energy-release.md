# Migrazione Spark 2 -> Spark 3 - gse-energy-release

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`gse-energy-release` è un progetto multi-modulo che calcola risultati energetici mensili/annuali e gestisce flussi di import/export (anche Sqoop) verso sistemi a valle.

### 1.2 Cosa sappiamo oggi dal documento esistente

Il progetto:
- è multi-modulo Maven (`common-module`, `gse-calcolo-mensile`, `gse-calcolo-annuale`),
- usa Spark `2.4.0.cloudera2` e Scala `2.11.12`,
- ha driver principali nei moduli mensile/annuale,
- contiene script deploy `run-*` e `spark-submit-*`.

### 1.3 Significato dei componenti (in parole non tecniche)

- **`common-module`**: logica condivisa e utility comuni.
- **`gse-calcolo-mensile`**: calcoli periodici mensili.
- **`gse-calcolo-annuale`**: calcoli periodici annuali.
- **`Driver.scala`**: orchestration del singolo modulo.
- **`deploy/*.sh`**: avvio operativo job, import/export e submit Spark.

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale:
- Spark: `2.4.0.cloudera2`
- Scala: `2.11.12`
- Java: `1.8`
- Build: Maven multi-modulo

Target:
- Spark 3.x
- Scala 2.12.x
- aggiornamento script/config per runtime moderno.

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` (root + moduli) - cosa cambiare, dove, e perché

### Obiettivo

Allineare tutti i moduli a Spark 3 + Scala 2.12.

### Checklist operativa

1. aggiornare versioni Spark/Scala nel parent
2. aggiornare artifact Spark `_2.12`
3. verificare dipendenze transitive nei moduli
4. riallineare librerie test/plugin.

### Errori tipici da principiante

- aggiornare solo il parent ma non i moduli,
- mismatch versioni tra moduli.

---

## 3.2 Codice Scala (`Driver`, controller, DAO) - cosa controllare concretamente

### Obiettivo

Garantire compatibilità Spark 3 senza regressioni business.

### Dove intervenire prima

1. `Driver.scala` mensile/annuale
2. controller prepare/transform
3. DAO comuni e di modulo.

### Cosa cambiare (pratico)

- verificare join/cast/date/null semantics Spark 3,
- controllare query SQL e schema output,
- verificare serializzazione e utility comuni.

### Config transitoria utile

- eventuali `spark.sql.legacy.*` solo in fase di allineamento iniziale.

### Errori tipici da principiante

- non confrontare output mensile e annuale separatamente,
- aggiornare codice senza riallineare script deploy.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire i due moduli in modo stabile su Spark 3.

### Cosa verificare

1. `run-gse-energy-release-calcolo-mensile.sh`
2. `run-gse-energy-release-calcolo-annuale.sh`
3. `spark-submit-gse-calcolo-mensile.sh`
4. `spark-submit-gse-calcolo-annuale.sh`
5. `params.properties` + profili config.

### Errori tipici da principiante

- script submit non allineati al nuovo runtime,
- conf diversi tra modulo mensile e annuale senza controllo.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna parent + moduli pom
2. Porta compilazione in verde
3. Migra/valida driver e DAO comuni
4. Aggiorna script deploy
5. Esegui test modulo mensile
6. Esegui test modulo annuale
7. Confronta output con baseline.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- test già presenti: `PrepareTest`, `TransformTest`, `EnvironmentSparkTest`,
- test controller comuni in `common-module`.

## 4.2 Integration test - test end-to-end

- run completo mensile,
- run completo annuale,
- confronto output `GSE_AGGR_M` / `GSE_AGGR_A` con baseline.

## 4.3 Test non funzionali

- tempi run mensile/annuale,
- stabilità su run ripetute,
- verifica integrità pipeline sqoop+spark+sqoop.

## 4.4 Criteri di accettazione finali

1. Output coerente col legacy (scostamenti documentati)
2. Nessun errore runtime Spark 3
3. Script deploy funzionanti per entrambi i moduli
4. Stabilità su più esecuzioni consecutive.
