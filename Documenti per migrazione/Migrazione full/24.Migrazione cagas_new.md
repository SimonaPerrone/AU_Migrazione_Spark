# Migrazione Spark 2 -> Spark 3 - cagas

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`cagas` calcola il consumo annuo gas (CA) e dataset correlati:
- validazione misure,
- consumi,
- CA,
- pre-final e final.
Supporta sessioni `CDP`, `CCG_FIN`, `CCG_RIC` e può essere orchestrato insieme a `freezer_pre_calcolo`.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8;
- ha entrypoint `it.sferanet.au.App` (in `cagas/source`);
- seleziona environment per sessione;
- ha script `run_ca.sh`, `run_cdp.sh`, `run_cdp_ccg.sh`, `spark2-submit-CAGas.sh`;
- in run CDP/CCG viene richiamato prima il freezer.

(Riferimenti: `Documenti per migrazione/24.Migrazione cagas.md`, `cagas/source/*`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parsing `-p`, `-s`, `-d` e validazione sessione.
- **`driver`**: `App` orchestration dell’intera pipeline CA.
- **`factory`**: `FlowFactory` e filtri lancio (massivo/filtrato).
- **`flow`**: estrazione misure -> validazione -> consumi -> CA -> finalizzazione.
- **`model`**: modelli `Flow` e dati dominio.
- **`dao/controller/utility`**: lettura rcu/rcugas, business controller e utility ambiente.

(Riferimenti: `App.scala`, `utilities/args/FlowArgsFactory.scala`, package controller/dal)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE)

(Riferimenti: `cagas/source/pom.xml`, script deploy spark-submit)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

`run_ca.sh` lancia `it.sferanet.au.App`; script `run_cdp*.sh` orchestrano freezer + CA.

### Step 2 - Lettura parametri e config

`FlowArgsFactory` valida sessione (`CDP/CCG_FIN/CCG_RIC`) e data opzionale.

### Step 3 - Inizializzazione Spark

`App` imposta environment sessione-specifico.

### Step 4 - Lettura input

Lettura misure, anagrafica rcugas/rcu, tds, lookup climatici, pesi.

### Step 5 - Pulizia e normalizzazione

Filtri lancio, forzature, esclusioni, deduplica e selezione ultima versione misure.

### Step 6 - Regole di business (flow)

Pipeline:
- VALIDAZIONE,
- CONSUMI,
- CA,
- CA_PRE_FINAL,
- CA_FINAL.

### Step 7 - Costruzione dataset finale

Generazione dataset output con enrichment e ricalcoli necessari.

### Step 8 - Scrittura output

Scrittura tabelle validation/consumption/ca/pre-final/final + cleanup temporanei.

### Step 9 - Chiusura e logging

Log di fine processo e gestione errori.

(Riferimenti base del flusso: `App.scala`, `run_ca.sh`, `run_cdp.sh`, `run_cdp_ccg.sh`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare la pipeline CA a Spark3 senza regressioni business.

(Riferimento: `cagas/source/pom.xml`)

### Checklist operativa

1. Spark -> `3.5.x`
2. Scala -> `2.12.x`
3. artifact Spark `_2.12`
4. aggiornamento librerie test/plugin
5. verifica shading/build con profili.

### Errori tipici da principiante

- dimenticare aggiornamenti sotto `source/`;
- mismatch dipendenze scala;
- ignorare warning test runtime.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Conservare identico risultato su `CDP`, `CCG_FIN`, `CCG_RIC`.

(Riferimento: `App.scala`, controller e DAL)

### Dove intervenire prima

1. parsing + environment;
2. fasi validation/consumption/ca;
3. pre-final/final e cleanup.

### Cosa cambiare (pratico)

- cast e null handling espliciti;
- gestione date/timestamp Spark3;
- verificare join tra tabelle RCU/RCUGAS/TDS;
- controllare conversioni RDD <-> DataFrame.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` solo ponte.

### Errori tipici da principiante

- testare solo sessione CDP;
- non verificare output finale arricchito.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire su CDP con catena freezer + CA.

(Riferimento: `spark2-submit-CAGas.sh`, `run_ca.sh`, `run_cdp.sh`, `run_cdp_ccg.sh`)

### Cosa verificare

1. sostituire `spark2-submit` con submit Spark3;
2. riallineare conf risorse (executor/driver/overhead);
3. `kinit -kt` valido su YARN prima run;
4. in CDE usare credenziali/profile CDE;
5. passare config con `--files` e non dipendere da FS locale.

### Errori tipici da principiante

- migrare solo `run_ca.sh`;
- disallineare properties tra cagas e freezer;
- path output non coerenti tra sessioni.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra build cagas.
2. Migra bootstrap/environment.
3. Migra validation+consumption.
4. Migra CA/pre-final/final.
5. Aggiorna script cagas e orchestrazione freezer.
6. Testa su tutte le sessioni.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parser args/sessione;
- utility di filtraggio e deduplica;
- funzioni controller isolate.

## 4.2 Integration test - test end-to-end

- run completo `CDP`;
- run completo `CCG_FIN`;
- run completo `CCG_RIC`;
- confronto Spark2 vs Spark3 su validation/consumption/ca/final.

(Riferimento: pipeline `App.run()`)

## 4.3 Test non funzionali

- tempi run completi;
- stabilità su rilanci;
- idempotenza output finali.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline CA corrente)

## 5. Glossario minimo (per orientarti subito)

- **CA**: consumo annuo gas.
- **TDS**: informazioni tecniche usate nei calcoli.
- **Pre-final / final**: stadi progressivi dell’output finale.
- **Freezer**: preparazione dati precedente al calcolo CA.
- **DAL/DAO**: accesso alle tabelle sorgenti/target.
- **Idempotenza**: rieseguire senza alterare il risultato atteso.
