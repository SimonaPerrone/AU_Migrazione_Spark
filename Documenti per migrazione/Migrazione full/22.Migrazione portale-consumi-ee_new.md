# Migrazione Spark 2 -> Spark 3 - portale-consumi-ee

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`portale-consumi-ee` è un progetto multi-modulo che alimenta il portale consumi elettrico.
Comprende:
- `calcolo_forniture` (costruzione forniture/info),
- `export_misure` (export 3M/33M, anche verso Mongo),
- `storico_misure_ee` (storicizzazione misure 3M/33M),
- `common` (librerie/config condivise).

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è multi-modulo Maven con parent `portale-consumi-ee/pom.xml`;
- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8;
- ha entrypoint `it.eng.au.portale_consumi_ee.Main` in più moduli;
- usa script deploy dedicati con `spark2-submit`;
- in `export_misure` è presente `mongo-spark-connector_2.11:2.4.3`.

(Riferimenti: `Documenti per migrazione/22.Migrazione portale-consumi-ee.md`, `portale-consumi-ee/*`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parsing parametri (`flow`, `storico`, path properties).
- **`driver`**: base comune (`common.Driver`) da cui partono i main modulo.
- **`factory`**: non centrale; dispatch interno via match su parametri.
- **`flow`**: flow calcolo forniture, export full/initialization, storico 3M/33M.
- **`model`**: strutture dati modulo-specifiche.
- **`dao/controller/utility`**: accesso dati Hive/Mongo e utility ambiente.

(Riferimenti: `calcolo_forniture/.../Main.scala`, `export_misure/.../Main.scala`, `storico_misure_ee/.../Main.scala`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven` multi-modulo

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE)

(Riferimenti: `portale-consumi-ee/pom.xml`, poms moduli, script submit)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Ogni modulo ha il suo script:
- `spark-submit-calcolo-forniture.sh`
- `spark-submit-export-misure.sh`
- `spark-submit-misure-storico.sh`

### Step 2 - Lettura parametri e config

I main leggono args/properties (flow e flag storico dove previsto).

### Step 3 - Inizializzazione Spark

Creazione `SparkSession` con environment modulo-specifico.

### Step 4 - Lettura input

Lettura da Hive (misure, anagrafiche, staging) e, per export, integrazione Mongo.

### Step 5 - Pulizia e normalizzazione

Filtri e normalizzazioni su dataset 3M/33M e su dati forniture.

### Step 6 - Regole di business (flow)

- `calcolo_forniture`: pipeline forniture/switch/gdm/fasce.
- `export_misure`: `flowFull` o `flowInitialization` + ramo storico.
- `storico_misure_ee`: `Storico3M` o `Storico33M`.

### Step 7 - Costruzione dataset finale

Creazione dataset finali per forniture, storico ed export.

### Step 8 - Scrittura output

Scritture su Hive/stage e collection Mongo (dove previsto).

### Step 9 - Chiusura e logging

Logging per modulo e stop session.

(Riferimenti base del flusso: `Main.scala` moduli + script deploy)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Migrare parent + tutti i moduli in modo coerente.

(Riferimento: `portale-consumi-ee/pom.xml`, `calcolo_forniture/pom.xml`, `export_misure/pom.xml`, `storico_misure_ee/pom.xml`)

### Checklist operativa

1. Aggiorna parent:
   - Spark -> `3.5.x`
   - Scala -> `2.12.x`
2. Aggiorna artifact Spark `_2.12`.
3. Aggiorna dipendenze test/plugin.
4. Verifica modulo `export_misure`:
   - migrazione connettore Mongo a versione compatibile Spark3/Scala2.12.
5. Verifica packaging deploy di tutti i moduli.

### Errori tipici da principiante

- migrare solo parent e non i moduli;
- mantenere connector Mongo non compatibile;
- mismatch versioni Scala tra moduli.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Mantenere invariati i comportamenti 3M/33M e i flussi forniture/export.

(Riferimento: `Main.scala` dei tre moduli, package flow/dao)

### Dove intervenire prima

1. main + parsing args;
2. flow principali;
3. accessi dati e scritture finali.

### Cosa cambiare (pratico)

- adeguare cast/date/null in Spark3;
- verificare join/union e schema output;
- controllare compatibilità API Mongo connector.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` solo in fase ponte.

### Errori tipici da principiante

- non testare combinazioni `flow/storico`;
- validare Hive ma non Mongo.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire stabilmente i tre moduli su CDP.

(Riferimento: script deploy moduli + `common/src/main/resources/profiles/*/config.properties`)

### Cosa verificare

1. sostituire `spark2-submit` con submit Spark3;
2. conf risorse/dynamic allocation coerenti per ciascun modulo;
3. no credenziali hardcoded nei file runtime;
4. Kerberos ticket valido su YARN (`kinit -kt`);
5. su CDE: `CDE_CREDENTIALS_FILE`, `CDE_CONFIG_PROFILE`, `--files` per config distribuite.

### Errori tipici da principiante

- aggiornare solo uno script;
- lasciare parametri Spark2 non ottimali;
- usare path locali non visibili al cluster.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra parent.
2. Migra modulo `common`.
3. Migra `calcolo_forniture`.
4. Migra `storico_misure_ee`.
5. Migra `export_misure` (Mongo).
6. Aggiorna script e fai test integrato cross-modulo.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing args;
- utility comuni;
- trasformazioni isolate moduli.

## 4.2 Integration test - test end-to-end

- `calcolo_forniture` completo;
- `storico_misure_ee` 3M e 33M;
- `export_misure` full e initialization;
- confronto Spark2 vs Spark3 su count/KPI/schema.

- controllo uso memoria/partizioni.

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline modulo per modulo)

## 5. Glossario minimo (per orientarti subito)

- **Multi-modulo**: progetto Maven con più sotto-progetti.
- **3M/33M**: finestre temporali di storico misure.
- **Driver**: avvio job Spark.
- **Flow**: ramo logico eseguito in base ai parametri.
- **Connector Mongo**: libreria per leggere/scrivere Mongo da Spark.
- **Idempotenza**: riesecuzione coerente senza duplicare effetti.
