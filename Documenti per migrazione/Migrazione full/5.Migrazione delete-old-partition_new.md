# Migrazione Spark 2 -> Spark 3 - delete-old-partition

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`delete-old-partition` è un job batch Scala/Spark che pulisce partizioni vecchie delle tabelle Hive.  
Legge una lista di tabelle da configurazione, calcola quante partizioni mantenere in base alla retention, esegue il `DROP PARTITION` e cancella anche i path fisici su HDFS.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa Spark `2.4.0.cloudera2` con Scala `2.11.12`;
- ha entrypoint `it.eng.au.deleteOldPartition.Driver`;
- viene eseguito da script `run_delete_old_partition.sh` con `spark2-submit`.

(Riferimenti: `Documenti per migrazione/5.Migrazione delete-old-partition.md`, `delete-old-partition/pom.xml`, `delete-old-partition/src/main/resources/deploy/run_delete_old_partition.sh`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parametro path properties passato da script.
- **`driver`**: esegue tutta la procedura di cleanup.
- **`factory`**: non presente.
- **`flow`**: non presente.
- **`model`**: non presente come package dedicato.
- **`dao/controller/utility`**: utility ambiente/costanti/versione in `utility/*`.

(Riferimenti: `src/main/scala/it/eng/au/deleteOldPartition/{Driver.scala,utility/*}`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x`
- Scala: `2.12.x` (se Scala)
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `delete-old-partition/pom.xml`, `Documento Onboarding Cloudera CDP 7.1.9 v1.9.md`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Lo script deploy lancia `Driver` con path al file `params.properties`.

### Step 2 - Lettura parametri e config

`Environment.getOrCreate(...)` carica proprietà operative (`tables.to.optimize`, `num.partition.remain`, path log).

### Step 3 - Inizializzazione Spark

Viene creata SparkSession e filesystem handle.

### Step 4 - Lettura input

Per ogni tabella configurata:
- legge partizioni con `SHOW PARTITIONS`,
- legge location tabella con `DESC FORMATTED`.

### Step 5 - Pulizia e normalizzazione

Filtra partizioni (es. sessione `CCG`) e ordina per calcolare quali rimuovere.

### Step 6 - Regole di business (flow)

Applica retention: mantiene `num.partition.remain`, seleziona solo il surplus da cancellare.

### Step 7 - Costruzione dataset finale

Costruisce lista finale delle partizioni da eliminare.

### Step 8 - Scrittura output

Esegue:
- `ALTER TABLE ... DROP IF EXISTS PARTITION (...)`
- cancellazione path HDFS corrispondente.

### Step 9 - Chiusura e logging

Log completo di partizioni trovate, selezionate e cancellate.

(Riferimenti base del flusso: `Driver.scala`, `utility/environment/*`, `deploy/params.properties`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare il progetto a Spark 3 + stack compatibile.

(Riferimento: `delete-old-partition/pom.xml`)

### Checklist operativa

1. Aggiorna versioni:
   - `spark.version` -> `3.5.x`
   - `scala.version` -> `2.12.x`
   - `scala.compat.version` -> `2.12`
2. Aggiorna artifact Spark (`spark-core`, `spark-sql`, `spark-hive`) con suffisso corretto.
3. Aggiorna librerie compatibili Spark 3.
4. Rimuovi librerie obsolete (se presenti).
5. Aggiorna librerie test e plugin build.
6. Verifica packaging/shading.

### Errori tipici da principiante

- lasciare dipendenze `_2.11`;
- aggiornare Spark ma non Scala/plugin;
- non controllare incompatibilità transitive.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Rendere il codice compatibile con Spark 3.

(Riferimento: `Driver.scala`, `utility/environment/*`)

### Dove intervenire prima

1. `Driver.scala`
2. utility environment
3. utility parsing partizioni/log

### Cosa cambiare (pratico)

- Verificare output e parsing di `SHOW PARTITIONS`/`DESC FORMATTED`.
- Verificare API Spark SQL usate in driver.
- Rafforzare gestione null/empty su partizioni e path.
- Garantire delete sicuro (no path non validi).

### Config transitoria utile

- `spark.sql.legacy.*` solo se emergono differenze su metadata SQL.

### Errori tipici da principiante

- non testare query metadata su Spark3;
- drop partizioni corretto ma delete path incoerente.

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Far girare correttamente il job su cluster Spark 3.

(Riferimento: `deploy/run_delete_old_partition.sh`, `profiles/*/config.properties`)

### Cosa verificare

1. Script `spark-submit` (class, jar, conf, risorse).
2. Parametri SQL (`spark.sql.adaptive.enabled`, `spark.sql.shuffle.partitions`, ecc.).
3. Compatibilità Hive Metastore/runtime target.
4. Path e permessi input/output/warehouse.

### Allineamenti onboarding CDP 7.1.9

- sostituire `spark2-submit` con submit Spark3;
- su YARN integrare Kerberos (`kinit -kt`, cleanup cache ticket);
- su CDE usare `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE`;
- in CDE evitare uso filesystem locale/NFS per dati operativi;
- evitare `spark.shuffle.service.enabled=true` in CDE.

### Errori tipici da principiante

- script migrato ma autenticazione non aggiornata;
- path properties errato tra HDFS e locale.

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: oggetto principale per usare Spark SQL/DataFrame.
- **DAO**: componente che legge/scrive dati da/verso sorgenti.
- **Flow**: sequenza di trasformazioni business.
- **Schema**: struttura colonne + tipi di un dataset.
- **Idempotenza**: rieseguire il job senza effetti collaterali non voluti.
