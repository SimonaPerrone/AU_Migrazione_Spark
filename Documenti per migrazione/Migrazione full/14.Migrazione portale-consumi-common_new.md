# Migrazione Spark 2 -> Spark 3 - portale-consumi-common

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`portale-consumi-common` è un modulo di **supporto operativo** (non un job Spark business): contiene script shell per manutenzione collezioni Mongo del Portale Consumi, in particolare backup e pulizia audit.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- contiene script `backup_collezione.sh` e `pulizia_dati_audit.sh`;
- usa profili `dev/prod` con `config.properties`;
- non espone un Driver Spark né package applicativi Scala di trasformazione dati.

(Riferimenti: `Documenti per migrazione/14.Migrazione portale-consumi-common.md`, `portale-consumi-common/src/main/resources/*`, `README.md`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: argomenti shell (`-c`, `-m`, `-d`, `-h`) nei due script.
- **`driver`**: non presente (assenza main Spark/Scala).
- **`factory`**: non presente.
- **`flow`**:
  - backup collezione Mongo (`*_BKP`)
  - pulizia dati audit più vecchi della soglia mesi
- **`model`**: non presente come modello dati applicativo.
- **`dao/controller/utility`**: non presenti come package Scala; logica in shell script.

(Riferimenti: `src/main/resources/deploy/backup_collezione.sh`, `pulizia_dati_audit.sh`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: **non applicabile** (nessun job Spark nel modulo)
- Scala/Python: proprietà Scala presenti in `pom.xml`, ma nessun codice Scala operativo
- Java: `1.8` (build)
- Build tool: `Maven`

Target:

- Runtime/cluster: CDP 7.1.9 (allineamento operativo script e sicurezza)
- Spark 3: impatto indiretto (solo se orchestrato insieme a job Spark migrati)

(Riferimenti: `portale-consumi-common/pom.xml`, struttura `src/main/resources`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

L’operatore lancia uno script deploy:
- `backup_collezione.sh`
- `pulizia_dati_audit.sh`

### Step 2 - Lettura parametri e config

Gli script leggono parametri CLI e proprietà da profilo (`deploy.path.local`, `deploy.path.logs`, `mongo.params.hdfs`, nomi collezioni audit).

### Step 3 - Inizializzazione ambiente

Impostazione log file e variabili ambiente script.

### Step 4 - Lettura input

Lettura URI e DB Mongo via `hdfs dfs -cat` dal file properties condiviso.

### Step 5 - Pulizia e normalizzazione

Validazione argomenti:
- `backup_collezione`: obbligo `-c`
- `pulizia_dati_audit`: `-m` con soglia minima 24 mesi

### Step 6 - Regole di business (flow)

- backup: `aggregate {$out: "<collection>_BKP"}`
- pulizia audit: `$pull` sugli array audit con data `< data_soglia`

### Step 7 - Costruzione dataset finale

Non costruisce dataset Spark; aggiorna collezioni Mongo.

### Step 8 - Scrittura output

Scrittura log e aggiornamento/backup collezioni audit.

### Step 9 - Chiusura e logging

Chiusura script con exit code e messaggi operativi.

(Riferimenti base del flusso: `deploy/backup_collezione.sh`, `deploy/pulizia_dati_audit.sh`, `profiles/*/config.properties`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Allineare il modulo al ruolo reale (utility script) nel contesto CDP 7.1.9.

(Riferimento: `portale-consumi-common/pom.xml`)

### Checklist operativa

1. Verifica se mantenere proprietà Scala/plugin (non essendoci codice Scala).
2. Aggiorna plugin Maven a baseline aziendale.
3. Mantieni copia risorse deploy/profili in `target/deploy`.
4. Evita dipendenze Spark non necessarie in questo modulo.

### Errori tipici da principiante

- trattare il modulo come job Spark quando non lo è;
- aggiungere dipendenze inutili;
- non mantenere la pipeline di packaging risorse.

---

## 3.2 Script shell - cosa controllare concretamente

### Obiettivo

Rendere robusti backup e pulizia audit nel nuovo ambiente.

(Riferimento: script deploy)

### Dove intervenire prima

1. `backup_collezione.sh`
2. `pulizia_dati_audit.sh`
3. `profiles/*/config.properties`

### Cosa cambiare (pratico)

- hardening script (`set -euo pipefail` se compatibile);
- validazione input e messaggi errore chiari;
- gestione credenziali/endpoint Mongo coerente con CDP;
- revisione comandi `hdfs dfs` e `mongosh` nel nuovo runtime.

### Config transitoria utile

- non applicabile lato Spark SQL; focus su variabili ambiente e path.

### Errori tipici da principiante

- cambiare path profilo senza aggiornare script;
- non testare soglia minima `-m` e casi limite;
- non verificare permessi su HDFS/Mongo.

---

## 3.3 Configurazione runtime (properties + orchestrazione)

### Obiettivo

Mantenere operatività script in sicurezza su CDP 7.1.9.

(Riferimento: `profiles/dev/config.properties`, `profiles/prod/config.properties`)

### Cosa verificare

1. path `deploy.path.local` e `deploy.path.logs`;
2. `mongo.params.hdfs` raggiungibile;
3. nomi collezioni audit corretti per ambiente;
4. permessi utente tecnico su HDFS e Mongo.

### Errori tipici da principiante

- usare profilo dev in produzione;
- non prevedere rotazione log;
- eseguire cleanup senza backup valido.

### Allineamenti onboarding CDP 7.1.9

- usare canali autenticati/permessi coerenti (Ranger/Knox dove applicabile);
- evitare dipendenze da path locali non governati;
- mantenere segregazione config per ambiente.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Conferma ruolo utility-only del modulo.
2. Allinea profili/path con nuovo ambiente.
3. Hardening script + validazione error handling.
4. Test backup e cleanup in DEV.
5. Promozione in PROD con runbook operativo.

---

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- test argomenti script (`-h`, parametri mancanti, valori non validi);
- test soglia `-m` minima;
- test naming collezioni backup.

## 4.2 Integration test - test end-to-end

- backup collezione reale di test;
- pulizia audit con data soglia;
- verifica contenuti post-esecuzione in Mongo.

(Riferimento: `src/test/sh/test_backup_collezione.txt`, `test_pulizia_dati_audit.txt`)

## 4.3 Test non funzionali

- tempi esecuzione su collezioni grandi;
- idempotenza run ripetute;
- gestione log e spazio disco.

## 4.4 Criteri di accettazione finali

1. Backup creato correttamente (`*_BKP`)
2. Pulizia audit conforme alla soglia temporale
3. Nessun errore operativo su HDFS/Mongo
4. Stabilità su run pianificate

---

## 5. Glossario minimo (per orientarti subito)

- **Utility module**: modulo di supporto operativo, non pipeline Spark.
- **Audit**: storico eventi/azioni su entità business.
- **Backup collezione**: copia di sicurezza della collezione Mongo.
- **Runbook**: procedura operativa standard di esecuzione/rollback.
- **Idempotenza**: rieseguibilità senza effetti collaterali indesiderati.
