# Migrazione Spark 2 -> Spark 3 - erp-e-profilazione-punti-no

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`erp-e-profilazione-punti-no` (modulo `ERP`) esegue calcoli ERP su più flow: `DIST`, `TERNA`, `IP`, `INT`, `FULL`, `NO`, `SALDO`, `DATI`.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è parent + modulo `ERP`;
- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8;
- entrypoint `it.eng.au.ERP.Main`;
- routing flow via `ERPArgs` e `Main.scala`;
- submit script `spark-submit-erp.sh`.

(Riferimenti: `Documenti per migrazione/28.Migrazione erp-e-profilazione-punti-no.md`, `erp-e-profilazione-punti-no/*`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: valida flow richiesto e path properties/pod esclusi.
- **`driver`**: base run.
- **`factory`**: routing per flow nel main.
- **`flow`**: classi dedicate per DIST/TERNA/IP/INT/FULL/NO/SALDO/DATI.
- **`model`**: strutture dati ERP.
- **`dao/controller/utility`**: letture, calcoli, output e helper operativi.

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven` (parent + modulo)

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9

## 2. Funzionamento step by step

### Step 1 - Avvio job

`spark-submit-erp.sh` lancia `it.eng.au.ERP.Main`.

### Step 2 - Lettura parametri e config

`ERPArgs.parse` valida flow, properties e path pod esclusi.

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate(...)` crea SparkSession.

### Step 4 - Lettura input

Lettura dataset ERP e file supporto.

### Step 5 - Pulizia e normalizzazione

Filtri iniziali e normalizzazione input.

### Step 6 - Regole di business (flow)

Dispatch sul flow scelto (`DIST`, `TERNA`, `IP`, `INT`, `FULL`, `NO`, `SALDO`, `DATI`).

### Step 7 - Costruzione dataset finale

Elaborazione risultato per flow.

### Step 8 - Scrittura output

Scrittura output ERP su tabelle/path previsti.

### Step 9 - Chiusura e logging

Fine run con logging tecnico.

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Migrare parent+modulo ERP mantenendo compatibilità multi-flow.

### Checklist operativa

1. Spark -> `3.5.x`
2. Scala -> `2.12.x`
3. artifact Spark `_2.12`
4. aggiornare plugin/test e filtri risorse;
5. verificare shading del modulo `ERP`.

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Garantire output equivalente su tutti i flow ERP.

### Dove intervenire prima

1. `ERPArgs`/parsing;
2. `Main.scala` dispatch;
3. flow ad alto impatto (`FULL`, `DIST`, `TERNA`, `SALDO`).

### Cosa cambiare (pratico)

- cast/date/null handling;
- join/aggregazioni Spark SQL 3;
- validazione output su flow NO e DATI.

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Run robusto su CDP/CDE.

### Cosa verificare

1. submit Spark3;
2. tuning executor/driver/shuffle;
3. Kerberos (`kinit -kt`) su YARN;
4. in CDE usare `CDE_CREDENTIALS_FILE` e `CDE_CONFIG_PROFILE`;
5. usare `--files` per config distribuite.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra pom parent/modulo.
2. Migra parser+dispatch.
3. Migra flow principali.
4. Aggiorna script runtime.
5. Testa tutti i flow.
6. Promuovi su QA.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parse args e validazione flow;
- utility trasformazioni;
- funzioni core per singolo flow.

## 4.2 Integration test - test end-to-end

- run completo per ogni flow (`DIST/TERNA/IP/INT/FULL/NO/SALDO/DATI`);

## 4.3 Test non funzionali

- benchmark flow pesanti;
- stabilità su rilanci;
- idempotenza output.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

## 5. Glossario minimo (per orientarti subito)

- **Flow ERP**: variante di calcolo ERP.
- **Dispatch**: scelta flow in base ai parametri.
- **SALDO**: fase di consolidamento finale.
- **POD esclusi**: elenco punti da non considerare.
- **Idempotenza**: riesecuzione coerente.
- **Shading**: packaging jar con dipendenze.
