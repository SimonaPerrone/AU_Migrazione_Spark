# Migrazione Spark 2 -> Spark 3 - aggregatore-consumi-agg

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`aggregatore-consumi-agg` pubblica i consumi gas dei processi AGG/SBG e genera report SBG.
È un progetto multi-modulo con pipeline batch che legge `daily_consumption`, applica regole di sterilizzazione/coefficiente e produce file/tabelle finali.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è multi-modulo (`aggregatore-common`, `aggregatore-agg`, `aggregatore-sbg`, `query-report-sbg`);
- usa Spark `2.4.0.cloudera2`, Scala `2.11.12`, Java 8;
- ha driver separati per AGG, SBG e query report;
- usa script `run_aggregatore_agg.sh`, `run_aggregatore_sbg.sh`, `run_report_sbg.sh`.

(Riferimenti: `Documenti per migrazione/26.Migrazione aggregatore-consumi-agg.md`, `aggregatore-consumi-agg/*`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parametri run (properties e opzionali output couples per SBG).
- **`driver`**: avvia la procedura per AGG, SBG o report.
- **`factory`**: seleziona aggregatori/query da eseguire.
- **`flow`**: pipeline su consumi + incoerenti + esclusi.
- **`model`**: schema logico record di input/output.
- **`dao/controller/utility`**: accesso a tabelle consumi, coefficienti, log di processo.

(Riferimenti: `aggregatore-agg/.../Driver.scala`, `aggregatore-sbg/.../Driver.scala`, `query-report-sbg/.../Driver.scala`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven` multi-modulo

Target:

- Spark: `3.x`
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE)

(Riferimenti: `aggregatore-consumi-agg/pom.xml`, poms moduli, script deploy)

## 2. Funzionamento step by step

### Step 1 - Avvio job

Script AGG/SBG/report avviano i rispettivi Driver.

### Step 2 - Lettura parametri e config

I driver leggono properties e impostano variabili run.

### Step 3 - Inizializzazione Spark

`Environment.getOrCreate(...)` apre Spark context e logging.

### Step 4 - Lettura input

Lettura `daily_consumption`, `incoerenti`, `esclusi`.

### Step 5 - Pulizia e normalizzazione

Join su chiavi (`pdr`, `date`, `session`, `executionid`) e valorizzazione campi sterilizzati.

### Step 6 - Regole di business (flow)

Factory seleziona aggregatori/query; se serve, applica `CoefficientController`.

### Step 7 - Costruzione dataset finale

Produzione dataset aggregati/report per i processi richiesti.

### Step 8 - Scrittura output

Scrittura output e repair metadata (`MSCK REPAIR TABLE`) dove previsto.

### Step 9 - Chiusura e logging

Log iniziale/finale e chiusura processo.

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Migrare in modo coerente parent + tutti i moduli.

(Riferimento: `aggregatore-consumi-agg/pom.xml` + poms modulo)

### Checklist operativa

1. Spark -> `3.5.x`
2. Scala -> `2.12.x`
3. artifact Spark `_2.12`
4. allineare dipendenze tra moduli (`aggregatore-common`, `aggregatore-agg`, `aggregatore-sbg`, `query-report-sbg`)
5. aggiornare plugin build/test.

### Errori tipici da principiante

- aggiornare solo un modulo;
- mismatch versioni scala fra moduli;
- non verificare dipendenze transitive comuni.

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Conservare output AGG/SBG/report invariati.

(Riferimento: driver e factory moduli)

### Dove intervenire prima

1. driver AGG/SBG/report;
2. factory aggregatori/query;
3. join/sterilizzazione/coefficienti.

### Cosa cambiare (pratico)

- verificare cast/date/null;
- verificare join e overwrite colonne value;
- controllare semantica Spark SQL 3.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` solo in fase ponte.

### Errori tipici da principiante

- testare solo AGG e non SBG/report;
- non confrontare KPI finali.

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire i moduli su CDP 7.1.9 in modo stabile.

(Riferimento: `run_aggregatore_agg.sh`, `run_aggregatore_sbg.sh`, `run_report_sbg.sh`)

### Cosa verificare

1. migrare `spark2-submit` -> submit Spark3;
2. tuning executor/memory/shuffle;
3. Kerberos valido (`kinit -kt`) su YARN;
4. in CDE usare `CDE_CREDENTIALS_FILE`/`CDE_CONFIG_PROFILE`;
5. distribuire config con `--files` (no dipendenze locali/NFS).

### Errori tipici da principiante

- mantenere conf Spark2 non più adatte;
- non allineare properties tra moduli;
- cleanup tmp non gestito correttamente.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra parent/common.
2. Migra AGG.
3. Migra SBG.
4. Migra query-report.
5. Aggiorna script runtime.
6. Esegui test end-to-end.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing argomenti;
- factory aggregatori/query;
- trasformazioni isolate su value/sterilizzazione.

## 4.2 Integration test - test end-to-end

- run AGG completo;
- run SBG completo;
- run query report SBG;
- confronto Spark2 vs Spark3 su output e KPI.

## 4.3 Test non funzionali

- performance per modulo;
- stabilità run ripetute;
- idempotenza e coerenza output.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

## 5. Glossario minimo (per orientarti subito)

- **AGG/SBG**: processi gas di aggiustamento e bilanciamento.
- **Sterilizzazione**: sostituzione valore con valore corretto in caso di anomalie.
- **Incoerenti/Esclusi**: record fuori regola gestiti separatamente.
- **Factory**: seleziona i processi da lanciare.
- **Idempotenza**: riesecuzione senza effetti collaterali.
- **MSCK REPAIR**: riallineamento metadati Hive.
