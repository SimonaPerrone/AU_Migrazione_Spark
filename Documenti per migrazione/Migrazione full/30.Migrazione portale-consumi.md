# 30.Migrazioneportale-consumi.md

## 1) Descrizione Progetto

### 1.1 Obiettivo e perimetro
`portale-consumi` contiene il progetto storico `flusso-misure-master`, orchestrato tramite CLI (`FlussoMisureTool`) per ingestione, ammissibilità, aggregazioni, SEM, commit e funzioni portale consumi/export.

### 1.2 Stack tecnologico attuale
- **Spark `1.6.0-cdh5.12.1`** (non Spark 2)
- Scala `2.10.x`
- Hadoop `2.6 cdh`
- Maven legacy con plugin/versioni datate
- Script runtime: `flusso-misure-pc.sh`, `flusso-misure-pc2.sh`

### 1.3 Architettura logica
- Entrypoint: `it.au.misure.cli.FlussoMisureTool`
- `FlussoMisureTool` effettua parsing CLI e instrada ai comandi:
  - decompressione file
  - ingestion
  - ammissibilità
  - aggregazioni
  - commit
  - SEM
  - procedure portale consumi/export Mongo
- Script esterni passano opzioni runtime e classpath JDBC.

### 1.4 Punti sensibili per Spark 3
- Migrazione **non diretta Spark 2→3**: base attuale è Spark 1.6/Scala 2.10.
- Dipendenze legacy (`spark-assembly_2.10`, `spark-xml_2.10`, vecchi plugin) da rifattorizzare.
- Possibile necessità di migrazione in due step (1.6→2.4→3.x) o refactoring completo.

## 2) Funzionamento step by step

1. Script shell lancia `FlussoMisureTool` con opzioni CLI.
2. Il tool parse gli argomenti e seleziona il comando.
3. Esegue la procedura corrispondente (ingestion/ammissibilità/aggregazione/portale/export).
4. Le procedure scrivono output su storage/tabelle target.

## 3) Modifiche da apportare ad ogni singola componente

### 3.1 `flusso-misure-master/pom.xml`
- Aggiornamento completo stack:
  - Spark 1.6 → Spark 3
  - Scala 2.10 → versione compatibile Spark 3
  - plugin build e dipendenze legacy.
- Rimozione/aggiornamento dipendenze obsolete non più supportate.

### 3.2 CLI e moduli applicativi
- Revisione `FlussoMisureTool` e comandi associati per compatibilità API Spark 3.
- Verifica di tutte le classi invocate dal dispatcher CLI.

### 3.3 Script runtime
- Allineare script launch a conf Spark 3 e classpath JDBC.
- Verificare parametri executor/driver su cluster target.

### 3.4 Strategia migrazione consigliata
- Definire step incrementale e ambiente di test dedicato, vista distanza tecnologica elevata.

## 4) Test da prevedere

### 4.1 Unit test
- Se presenti/recuperabili suite storiche, adeguarle a stack aggiornato.
- In assenza di copertura sufficiente, introdurre test minimi sui comandi CLI principali.

### 4.2 Integration test
- Test end-to-end sui comandi core (ingestion, ammissibilità, aggregazioni, portale/export).

### 4.3 Regression test
- Confronto output business con baseline storica su dataset campione.

### 4.4 Performance test
- Benchmark completo post-migrazione e tuning conf Spark 3.
