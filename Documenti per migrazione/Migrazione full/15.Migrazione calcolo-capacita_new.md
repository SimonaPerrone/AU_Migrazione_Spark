# Migrazione Spark 2 -> Spark 3 - calcolo-capacita

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`calcolo-capacita` calcola la capacità gas a partire da misure, perimetri e anagrafiche, con output su tabelle Hive e flussi di export.  
È un job batch orchestrato da script deploy (import dati, calcolo Spark, refresh, export).

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è un caso legacy “major migration” (Spark 1.6 + Scala 2.10);
- ha entrypoint `it.au.misure.calcolo_capacita.Main`;
- usa `CalcoloCtcFlow` e script operativi in `src/main/resources/deploy`.

(Riferimenti: `Documenti per migrazione/15.Migrazione calcolo-capacita.md`, `calcolo-capacita/pom.xml`, `src/main/scala/.../Main.scala`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: parametri run passati da script (`DATA_CALC`, `X`, `Y`, verbose).
- **`driver`**: `Main.scala` crea execution id, avvia flow e scrive output.
- **`factory`**: non presente come package dedicato.
- **`flow`**: `CalcoloCtcFlow` contiene pipeline di trasformazione/calcolo.
- **`model`**: non separato come package principale; dominio gestito in `component/*`.
- **`dao/controller/utility`**: presenti in `component/{hdao,implementation,schema,utility}`.

(Riferimenti: `src/main/scala/it/au/misure/calcolo_capacita/*`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `1.6.0-cdh5.12.1`
- Scala/Python: `Scala 2.10.5` (+ script Python deploy)
- Java: `1.8`
- Build tool: `Maven`

Target:

- Spark: `3.x` (consigliato `3.5.x`)
- Scala: `2.12.x`
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE profilo `spark35-test`)

(Riferimenti: `calcolo-capacita/pom.xml`, `deploy/gas-calcolo-capacita-spark-submit.sh`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Lo script `gas-calcolo-capacita-spark-submit.sh` lancia la classe `Main`.

### Step 2 - Lettura parametri e config

Lo script passa i parametri business e carica `application.conf`/`log4j.properties` via `--files`.

### Step 3 - Inizializzazione Spark

Il job inizializza Spark tramite utility (`SparkImplicit`) con config deploy.

### Step 4 - Lettura input

Il flow legge misure/perimetri/anagrafica da Hive/HDFS.

### Step 5 - Pulizia e normalizzazione

Vengono applicati filtri, cast e normalizzazioni su input.

### Step 6 - Regole di business (flow)

`CalcoloCtcFlow.run()` applica la logica di calcolo capacità.

### Step 7 - Costruzione dataset finale

Il flow produce dataset risultato con schema finale capacità.

### Step 8 - Scrittura output

`ctcFlow.write(result)` persiste il risultato sulle tabelle/path target.

### Step 9 - Chiusura e logging

Fine job e logging operativo; script esterni gestiscono refresh/export.

(Riferimenti base del flusso: `Main.scala`, `flow/CalcoloCtcFlow.scala`, script deploy)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare un progetto legacy Spark1/Scala2.10 a Spark3/Scala2.12.

(Riferimento: `calcolo-capacita/pom.xml`)

### Checklist operativa

1. Aggiorna versioni:
   - `spark.version` -> `3.5.x`
   - `scala.version` -> `2.12.x`
   - `scala.minor.version` -> `2.12`
2. Aggiorna artifact Spark (`spark-core`, `spark-sql`, `spark-hive`) a `_2.12`.
3. Rimuovi dipendenze obsolete (`spark-assembly`, `spark-csv` legacy).
4. Aggiorna librerie compatibili Spark 3 (`spark-xml`, test libs, scalamock/scalatest).
5. Aggiorna plugin build e shading.

### Errori tipici da principiante

- lasciare dipendenze `_2.10`;
- migrare Spark senza migrare Scala;
- non verificare plugin test/build legacy.

---

## 3.2 Codice Scala/Python/Java - cosa controllare concretamente

### Obiettivo

Rendere il codice compatibile con Spark 3 senza regressioni business.

(Riferimento: `Main.scala`, `flow/*`, `component/*`)

### Dove intervenire prima

1. `Main.scala` + bootstrap Spark
2. `CalcoloCtcFlow.scala`
3. componenti `hdao/implementation/utility`

### Cosa cambiare (pratico)

- sostituire API Spark legacy con API Spark 3;
- esplicitare cast/date/null handling;
- verificare join/union e semantica SQL;
- riallineare eventuali script Python collegati alla pipeline.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` (solo ponte iniziale).

### Errori tipici da principiante

- portare a compilazione ma non confrontare output business;
- ignorare differenze Spark SQL su date e null.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Eseguire correttamente la pipeline su cluster Spark3/CDP.

(Riferimento: `deploy/gas-calcolo-capacita-spark-submit.sh`, `profiles/*/config.properties`)

### Cosa verificare

1. comando submit Spark3 e conf risorse;
2. parametri `parallelism`/`shuffle`/`memoryoverhead`;
3. path HDFS/Isilon e permessi;
4. script di import/refresh/export collegati.

### Errori tipici da principiante

- aggiornare solo jar e non gli script;
- mantenere tuning Spark1 non adatto a Spark3;
- usare path ambiente errati.

---

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna build/dependency.
2. Porta a compilazione pulita.
3. Migra codice flow/component.
4. Aggiorna script runtime.
5. Esegui test integrati.
6. Promuovi in QA/cluster.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing parametri;
- utility e trasformazioni isolate;
- cast/date/null.

## 4.2 Integration test - test end-to-end

- pipeline import -> calcolo -> refresh -> export;
- confronto Spark legacy vs Spark3:
  - row count
  - KPI capacità
  - schema output.

(Riferimento: flow principale e script deploy)

## 4.3 Test non funzionali

- performance su dataset reali;
- stabilità run ripetute;
- idempotenza/recovery.

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline processo corrente)

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: elaborazione dati a blocchi che termina.
- **SparkSession**: entrypoint principale Spark 3.
- **DAO**: componente di accesso ai dati.
- **Flow**: pipeline logica di trasformazioni.
- **Schema**: colonne e tipi del dataset.
- **Idempotenza**: rieseguibilità senza effetti collaterali.
