# Migrazione Spark 2 -> Spark 3 - indennizzi-misure-gas

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`indennizzi-misure-gas` è una suite batch multi-modulo che gestisce il ciclo completo degli indennizzi gas: calcolo, verifica ammissibilità rendiconti e pubblicazioni finali.  
In pratica prende dati da Hive/HDFS, applica regole business, produce tabelle/output di processo e, nei moduli di pubblicazione, genera i dataset finali per i sistemi a valle.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- è un **multi-modulo Maven** con 5 moduli applicativi;
- usa stack legacy Spark 2.4 + Scala 2.11;
- è eseguito con script shell `spark2-submit` per i moduli operativi.

(Riferimenti: `Documenti per migrazione/9.Migrazione indennizzi-misure-gas.md`, `indennizzi-misure-gas/pom.xml`, `indennizzi-misure-gas/*/src/main/resources/deploy/*.sh`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: legge i parametri di lancio (es. properties path, recovery, execution id).
- **`driver`**: avvia il processo e orchestra i passi del modulo.
- **`factory`**: presente in alcuni moduli (es. pubblicazione-indennizzi) per costruire componenti business.
- **`flow`**: non presente come package unico; la logica è nei `controller`.
- **`model`**: strutture dati e oggetti dominio.
- **`dao/controller/utility`**: lettura/scrittura dati, regole di trasformazione, ambiente Spark/log/config.

(Riferimenti:  
`calcolo-indennizzi/.../Driver.scala`,  
`ammissibilita-rendiconti/.../Driver.scala`,  
`pubblicazione-indennizzi/.../Driver.scala`,  
`pubblicazione-rendiconti/.../Driver.scala`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `2.4.0.cloudera2`
- Scala/Python: `Scala 2.11.12`
- Java: `8`
- Build tool: `Maven` (multi-modulo)

Target:

- Spark: `3.x`
- Scala: `2.12.x` (se Scala)
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

La migrazione è necessaria per allinearsi all’onboarding CDP 7.1.9 (runtime supportato, sicurezza Kerberos/CDE, vincoli Data Services, compatibilità Spark SQL più recente).

(Riferimenti: `indennizzi-misure-gas/pom.xml`, `Documenti per migrazione/Documento Onboarding Cloudera CDP 7.1.9 v1.9.md`)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Ogni modulo operativo parte dal proprio `Driver.scala`, tipicamente tramite script deploy:
- `run-calcolo-indennizzi.sh`
- `run-ammissibilita-rendiconti.sh`
- `run-pubblicazione-indennizzi.sh`
- `run-pubblicazione-rendiconti.sh`

### Step 2 - Lettura parametri e config

Gli script passano argomenti (`-p`, `-e`, `-r`, ecc.) e il job legge `params.properties` dai path deploy/HDFS.

### Step 3 - Inizializzazione Spark

Viene creata la SparkSession del modulo con configurazioni runtime (executor/driver/conf SQL/Hive).

### Step 4 - Lettura input

I DAO dei moduli leggono tabelle e path HDFS/Hive necessari al processo (dati misura/rendiconti/supporto).

### Step 5 - Pulizia e normalizzazione

Vengono applicati controlli qualità, normalizzazioni di formati e gestione record non coerenti.

### Step 6 - Regole di business (flow)

I controller applicano la logica core del modulo:
- calcolo indennizzi,
- regole ammissibilità rendiconti,
- arricchimenti/pubblicazioni finali.

### Step 7 - Costruzione dataset finale

Ogni modulo costruisce i dataset finali con schema coerente con le tabelle target.

### Step 8 - Scrittura output

Scrittura su Hive/HDFS e aggiornamento artefatti di processo (report/recovery/dataset pubblicati).

### Step 9 - Chiusura e logging

Chiusura con logging finale di esito e, dove previsto, gestione recovery/fasi successive.

(Riferimenti base del flusso: `indennizzi-misure-gas/*/src/main/scala/.../Driver.scala`, `indennizzi-misure-gas/*/src/main/resources/deploy/*`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare **tutta la suite multi-modulo** a Spark 3 + Scala 2.12, con build coerente.

(Riferimento: `indennizzi-misure-gas/pom.xml` + pom dei singoli moduli)

### Checklist operativa

1. Aggiorna versioni root:
   - `spark.version` -> `3.5.x` (o versione Spark3 target ambiente)
   - `scala.version` -> `2.12.x`
   - `scala.compat.version` -> `2.12`
2. Aggiorna artifact Spark `_2.12` in root/moduli:
   - `spark-core_2.12`
   - `spark-sql_2.12`
   - `spark-hive_2.12`
3. Aggiorna librerie test/plugin:
   - `scalatest_2.12`, surefire, scala-maven-plugin, shade.
4. Verifica compatibilità modulo `indennizzi-misure-gas-common` con i moduli applicativi.
5. Esegui allineamento dipendenze transitive in tutti i sottoprogetti.

### Errori tipici da principiante

- aggiornare solo il root pom ma non i moduli;
- lasciare dipendenze `_2.11`;
- avere versioni plugin diverse tra moduli con esiti build incoerenti.

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Rendere il codice compatibile con Spark 3 mantenendo invariata la logica business.

(Riferimento: package `controller`, `dao`, `utility` dei 4 moduli operativi)

### Dove intervenire prima

1. `calcolo-indennizzi` (modulo core del calcolo)
2. `ammissibilita-rendiconti`
3. `pubblicazione-indennizzi`
4. `pubblicazione-rendiconti`

### Cosa cambiare (pratico)

- cast espliciti su numerici/date/timestamp;
- gestione null più rigorosa in join/filtri;
- allineamento schema prima di union/join;
- verifica semantica Spark3 per funzioni SQL/DataFrame;
- validazione serializzazione/utility comuni nel modulo `common`.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` (solo ponte temporaneo)
- eventuali `spark.sql.legacy.*` solo se necessarie e poi da rimuovere

### Errori tipici da principiante

- correggere solo errori di compilazione senza confronto output;
- migrare tutti i moduli insieme senza baseline intermedia.

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Far girare i moduli su Spark3 rispettando i vincoli onboarding CDP 7.1.9.

(Riferimento: onboarding + script deploy modulo)

### Cosa verificare

1. Script `spark-submit`:
   - sostituire `spark2-submit` nei 4 script di run;
   - verificare conf executor/driver/memoryOverhead/shuffle.
2. Sicurezza YARN:
   - integrare autenticazione Kerberos (`kinit -kt`, `KRB5CCNAME`, cleanup).
3. Esecuzione su CDE (se scelta):
   - usare `CDE_CREDENTIALS_FILE` e `CDE_CONFIG_PROFILE` (`spark35-test`);
   - passare config con `--files`;
   - non usare filesystem locale/NFS per dati.
4. Configurazioni non supportate in CDE:
   - rimuovere/evitare `spark.shuffle.service.enabled=true`.
5. Path e permessi:
   - validare `hdfs.deploy.path`, `isilon.deploy.path`, cartelle hive/deploy/recovery;
   - verificare permessi Ranger/Knox/Kerberos secondo ambiente.

### Errori tipici da principiante

- script migrati a Spark3 ma senza aggiornare autenticazione;
- path locali ancora presenti in run CDE;
- mismatch proprietà tra moduli che rompe l’orchestrazione end-to-end.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna root pom + pom moduli (Spark3/Scala2.12).
2. Porta a compilazione pulita `indennizzi-misure-gas-common`.
3. Migra `calcolo-indennizzi` e valida output.
4. Migra `ammissibilita-rendiconti` e valida output.
5. Migra `pubblicazione-indennizzi` e `pubblicazione-rendiconti`.
6. Aggiorna tutti gli script deploy (submit + sicurezza).
7. Esegui regressione end-to-end multi-modulo.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing args/config per modulo
- utility e trasformazioni isolate
- gestione null/date/cast nei controller

## 4.2 Integration test - test end-to-end

- pipeline completa:
  - calcolo -> ammissibilità -> pubblicazione indennizzi -> pubblicazione rendiconti
- confronto Spark2 vs Spark3:
  - row count
  - chiavi business
  - KPI/aggregati
- verifica schema output per ogni modulo

(Riferimento: `Documenti per migrazione/9.Migrazione indennizzi-misure-gas.md`, sorgenti modulo)

## 4.3 Test non funzionali

- performance (tempo/memoria/shuffle)
- stabilità run ripetute
- recovery (es. `recovery.csv` in ammissibilità)

## 4.4 Criteri di accettazione finali

1. Output equivalente al legacy (o differenze documentate)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi
4. Esecuzione coerente dell’intera catena multi-modulo

(Riferimento: baseline progetto + onboarding CDP 7.1.9)

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: oggetto principale Spark per DataFrame/SQL.
- **DAO**: componente che legge/scrive dati.
- **Flow**: sequenza di regole e trasformazioni business.
- **Schema**: struttura colonne + tipi di un dataset.
- **Idempotenza**: rieseguire un job senza effetti collaterali indesiderati.
