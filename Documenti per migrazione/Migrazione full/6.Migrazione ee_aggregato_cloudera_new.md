# Migrazione Spark 2 -> Spark 3 - ee_aggregato_cloudera

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

`ee_aggregato_cloudera` è una suite Spark/Scala multi-comando per ingestione, aggregazioni, commit, SEM e processi collegati alle misure elettriche.  
L’entrypoint CLI smista il comando richiesto e avvia il modulo corrispondente.

### 1.2 Cosa sappiamo oggi dal documento esistente

Nel documento attuale è indicato che il progetto:

- usa stack legacy Spark `1.6.0-cdh5.12.1` e Scala `2.10.5`;
- ha entrypoint `it.au.misure.cli.FlussoMisureTool`;
- include moduli ingestione/aggregazioni/portale/sem, script deploy e `spark-defaults.conf` legacy.

(Riferimenti: `Documenti per migrazione/6.Migrazione ee_aggregato_cloudera.md`, `ee_aggregato_cloudera/source/pom.xml`, `source/src/main/scala/it/au/misure/cli/FlussoMisureTool.scala`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`args`**: opzioni CLI in `CommandLineOptions.scala`.
- **`driver`**: dispatcher principale `FlussoMisureTool.scala`.
- **`factory`**: non presente come package unico.
- **`flow`**: logica distribuita nei package `ingestione`, `aggregazioni`, `sem`, `portale`, `commit`.
- **`model`**: strutture dati distribuite nei moduli.
- **`dao/controller/utility`**: utility e componenti modulo-specifici.

(Riferimenti: `source/src/main/scala/it/au/misure/{cli,ingestione,aggregazioni,commit,sem,portale,util}`)

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:

- Spark: `1.6.0-cdh5.12.1`
- Scala/Python: `Scala 2.10.5`
- Java: `1.8`
- Build tool: `Maven` (`source/pom.xml`)

Target:

- Spark: `3.x`
- Scala: `2.12.x` (se Scala)
- Runtime/cluster: CDP 7.1.9 (YARN Spark3 o CDE `spark35-test`)

(Riferimenti: `source/pom.xml`, `source/spark-defaults.conf`, onboarding CDP 7.1.9)

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Gli script deploy (`flusso-misure.sh`, altri script bin) avviano il jar con `FlussoMisureTool`.

### Step 2 - Lettura parametri e config

`CommandLineOptions` parse le opzioni e identifica il comando (decompressione, ingestione, aggregazione, SEM, portale, commit, ecc.).

### Step 3 - Inizializzazione Spark

Viene creato il contesto Spark/Hive del comando richiesto con le conf runtime.

### Step 4 - Lettura input

Ogni comando legge sorgenti specifiche (Hive/HDFS/RCU/Oracle import tramite script sqoop).

### Step 5 - Pulizia e normalizzazione

Applica controlli e normalizzazioni proprie del comando (ingestione, validazioni, aggregazioni).

### Step 6 - Regole di business (flow)

Esecuzione della logica specifica modulo:
- ingestione misure,
- aggregazioni orarie/AM,
- SEM,
- portale consumi/export.

### Step 7 - Costruzione dataset finale

Genera dataset finali/intermedi per il modulo selezionato.

### Step 8 - Scrittura output

Scrive su tabelle/path target e, dove previsto, esegue passaggi integrativi (es. sqoop/report).

### Step 9 - Chiusura e logging

Log finale e stato processo.

(Riferimenti base del flusso: `FlussoMisureTool.scala`, `CommandLineOptions.scala`, script in `source/src/main/resources/deploy/bin/*`)

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `source/pom.xml` - cosa cambiare, dove, e perché

### Obiettivo

Portare il progetto a Spark 3 + stack compatibile.

(Riferimento: `ee_aggregato_cloudera/source/pom.xml`)

### Checklist operativa

1. Aggiorna versioni:
   - `spark.version` -> `3.5.x`
   - `scala.version` -> `2.12.x`
   - aggiornare compatibilità scala in tutti gli artifact
2. Aggiorna artifact Spark con suffisso corretto `_2.12`.
3. Rimuovi dipendenze obsolete (`spark-assembly_2.10`, connector non compatibili).
4. Aggiorna librerie compatibili Spark 3 (`spark-xml`, mongo connector, jdbc, ecc.).
5. Aggiorna librerie test e plugin build.
6. Verifica packaging/shading e Main-Class.

### Errori tipici da principiante

- lasciare dipendenze `2.10/2.11`;
- aggiornare solo Spark senza riallineare librerie esterne;
- non verificare plugin build legacy.

---

## 3.2 Codice Scala - cosa controllare concretamente

### Obiettivo

Rendere il codice compatibile con Spark 3.

(Riferimento: package `cli`, `ingestione`, `aggregazioni`, `sem`, `portale`, `commit`)

### Dove intervenire prima

1. `cli/FlussoMisureTool.scala` e `CommandLineOptions.scala`
2. moduli ingestione
3. moduli aggregazione e SEM
4. moduli portale/export

### Cosa cambiare (pratico)

- Migrare bootstrap verso `SparkSession` (eliminando API Spark 1.x obsolete).
- Verificare date/timestamp parsing e funzioni SQL legacy.
- Verificare null handling e cast espliciti.
- Verificare serializzazione/UDF e connettori esterni.

### Config transitoria utile

- `spark.sql.legacy.timeParserPolicy` (solo ponte)
- eventuali `spark.sql.legacy.*` temporanee

### Errori tipici da principiante

- migrare tutti i comandi insieme senza priorità;
- non confrontare output comando per comando.

---

## 3.3 Configurazione runtime (properties + spark-submit)

### Obiettivo

Far girare correttamente il job su cluster Spark 3.

(Riferimento: `source/spark-defaults.conf`, `source/src/main/resources/deploy/bin/*`, `profiles/*/config.properties`)

### Cosa verificare

1. Script `spark-submit` (class, jar, conf, risorse).
2. Parametri SQL (`spark.sql.adaptive.enabled`, `spark.sql.shuffle.partitions`, ecc.).
3. Compatibilità Hive Metastore/runtime target.
4. Path e permessi input/output/warehouse.

### Allineamenti onboarding CDP 7.1.9

- aggiornare script per Spark3;
- YARN: aggiungere Kerberos (`kinit -kt`, cleanup ticket cache);
- CDE: usare `CDE_CREDENTIALS_FILE` + `CDE_CONFIG_PROFILE`;
- in CDE evitare FS locale/NFS per dati;
- rimuovere conf non supportate CDE (`spark.shuffle.service.enabled=true`);
- aggiornare endpoint/TLS/driver JDBC secondo nuovo cluster.

### Errori tipici da principiante

- mantenere `spark-defaults.conf` legacy non compatibile;
- usare stessi path/parcels storici CDH non presenti in CDP.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Aggiorna build/dependency.
2. Porta a compilazione pulita.
3. Correggi codice impattato.
4. Aggiorna config runtime/submit.
5. Esegui test locali/integrati.
6. Promuovi in QA/cluster.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing args/config
- utility e trasformazioni isolate
- null/date/decimal/cast

## 4.2 Integration test - test end-to-end

- pipeline completa su dataset campione
- confronto Spark2 vs Spark3:
  - row count
  - chiavi business
  - KPI/aggregati
- verifica schema output (nomi/tipi/partizioni)

(Riferimento: comandi principali ingestione/aggregazioni/SEM/portale)

## 4.3 Test non funzionali

- performance (tempo/memoria)
- stabilità run ripetute
- idempotenza/recovery

## 4.4 Criteri di accettazione finali

1. Output equivalente (scostamenti documentati)
2. Nessun errore runtime su Spark 3
3. Stabilità su almeno 3 run consecutivi

(Riferimento: baseline attuale + onboarding CDP 7.1.9)

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: oggetto principale per usare Spark SQL/DataFrame.
- **DAO**: componente che legge/scrive dati da/verso sorgenti.
- **Flow**: sequenza di trasformazioni business.
- **Schema**: struttura colonne + tipi di un dataset.
- **Idempotenza**: rieseguire il job senza effetti collaterali non voluti.
