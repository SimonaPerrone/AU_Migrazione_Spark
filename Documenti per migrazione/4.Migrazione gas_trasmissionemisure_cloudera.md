# Migrazione Spark 2 -> Spark 3 - gas_trasmissionemisure_cloudera

## 1. Descrizione Progetto

### 1.1 A cosa serve questo progetto (spiegato semplice)

Questo progetto è un job batch PySpark che legge file (in particolare XML), valida nomenclatura/tracciato, estrae i record per diversi flussi (A01/A40/D01/SM1), e scrive output su parquet/Hive per usi downstream.

In pratica:
1. legge una lista file da query,
2. valida i file,
3. trasforma i contenuti,
4. pubblica dettaglio + tabella principale.

### 1.2 Cosa sappiamo oggi dal documento esistente

Dal materiale attuale risulta che il progetto:
- è Python/PySpark con entrypoint `source/pyspark2/Main.py`,
- usa componenti legacy Spark (`SparkContext`, `SQLContext`, `HiveContext`),
- gestisce parsing XML, validazioni XSD e scritture parquet con repair Hive.

(Riferimenti: codice in `source/pyspark2/Main.py`, `source/pyspark2/Ingestion.py`, `source/pyspark2/selectorFlusso.py`)

### 1.3 Significato dei componenti (in parole non tecniche)

- **`Main.py`**: legge parametri da linea comando e avvia il job.
- **`Params.py`**: contiene/trasporta i parametri operativi.
- **`Ingestion.py`**: cuore del processo (lettura file, validazioni, trasformazioni, scrittura).
- **`selectorFlusso.py`**: seleziona la logica specifica in base al flusso.
- **`source/conf/*.json` + `log4j.properties`**: configurazioni.
- **`source/bin/script/ca/*` e `source/bin/bonifica/*`**: script SQL/shell di supporto operativo.

### 1.4 Stack tecnico attuale e perché va migrato

Stack attuale rilevato:
- Spark API: pattern legacy (`SparkContext`, `SQLContext`, `HiveContext`)
- Linguaggio: Python (PySpark)
- Runtime: impostazione storica in stile CDH/Cloudera

Target:
- Spark 3.x con `SparkSession` come entry API standard,
- allineamento parser/semantica SQL Spark 3,
- runtime e script di submit compatibili con ambiente target attuale.

La migrazione è necessaria perché il codice usa API e convenzioni legacy meno manutenibili e più esposte a incompatibilità nel runtime moderno.

## 2. Funzionamento step by step

Di seguito il flusso logico completo, con spiegazione “cosa succede” e “perché”.

### Step 1 - Avvio job

Parte `main(argv)` in `source/pyspark2/Main.py`, con parsing opzioni (`-m`, `-f`, `-q`, `-e`, ecc.).

### Step 2 - Lettura parametri e config

Vengono valorizzati parametri come:
- `mode` (local/yarn),
- `flusso`,
- `query` o `query_file`,
- data (`giorno/mese/anno`),
- flag test/verbose.

### Step 3 - Inizializzazione Spark

`Ingestion.start()` chiama `set_spark_context(...)` che crea `SparkConf`, `SparkContext` e poi `HiveContext` (fallback `SQLContext`).

### Step 4 - Lettura input

Il job esegue query SQL per ottenere la lista file, filtra per flusso e legge i contenuti con `wholeTextFiles`.

### Step 5 - Pulizia e normalizzazione

Esegue decode UTF-8 e trasformazione iniziale dei file XML in strutture utilizzabili.

### Step 6 - Regole di business (flow)

Applica:
- validazione nomenclatura file (`valida_nomenclatura`),
- validazione XSD (`valida_flussoXSD`),
- parsing per flusso (`parse` + `selectorFlusso`),
- separazione validi/non validi e costruzione record dettaglio/principale.

### Step 7 - Costruzione dataset finale

Crea DataFrame di output con colonne di esito, metadati file, codici causale, data elaborazione, campi servizio/flusso.

### Step 8 - Scrittura output

Scrive parquet partizionato (es. `t_anno_caricamento`, `t_mese_caricamento`, `t_tipo_servizio`) e lancia `MSCK REPAIR TABLE`.

### Step 9 - Chiusura e logging

Registra esiti, warning e fine elaborazione.

## 3. Modifiche da apportare per componente (guida pratica per principiante)

## 3.1 `pyspark2/Ingestion.py` - cosa cambiare, dove, e perché

### Obiettivo

Portare il job da API legacy a API Spark 3 stabili e supportate.

### Checklist operativa

1. Sostituire bootstrap legacy:
   - da `SparkContext + SQLContext/HiveContext`
   - a `SparkSession.builder...getOrCreate()`.
2. Spostare tutte le `setConf` su `spark.conf.set(...)` (o builder conf).
3. Verificare funzioni SQL/hive (`MSCK REPAIR TABLE`, show/select) su Spark 3.
4. Riesaminare UDF e cast impliciti per robustezza in Spark 3.
5. Validare lettura/scrittura parquet e partizionamento.

### Errori tipici da principiante

- tenere `HiveContext` nel codice anche dopo upgrade runtime;
- aggiornare runtime ma non conf;
- non ricontrollare compatibilità query SQL storiche.

---

## 3.2 `Main.py`, `Params.py`, `selectorFlusso.py` - cosa controllare concretamente

### Obiettivo

Mantenere la stessa logica funzionale, adeguando solo compatibilità runtime/API.

### Dove intervenire prima

1. `Main.py`: parsing argomenti e passaggio parametri.
2. `Params.py`: allineamento opzioni per nuove conf runtime.
3. `selectorFlusso.py`: verificare routing corretto dei flussi dopo migrazione.

### Cosa cambiare (pratico)

- rendere espliciti parametri obbligatori e validazioni;
- uniformare logging/gestione errori;
- verificare che la selezione flusso non dipenda da comportamenti legacy impliciti.

### Config transitoria utile

Se emergono differenze su parsing date/sql:
- valutare `spark.sql.legacy.*` solo come ponte temporaneo.

### Errori tipici da principiante

- cambiare insieme logica business e migrazione tecnica;
- non testare ogni flusso separatamente (A01/A40/D01/SM1).

---

## 3.3 Configurazione runtime (properties + script)

### Obiettivo

Far girare correttamente il job su Spark 3 senza regressioni operative.

### Cosa verificare

1. **Config file**:
   - `source/conf/calcoloProfStd.json`
   - `source/conf/functions.json`
   - `source/conf/log4j.properties`
2. **Script operativi**:
   - `source/bin/script/ca/*` (SQL/shell),
   - `source/bin/bonifica/*`,
   - eventuali script di avvio flusso.
3. **Conf Spark SQL principali**:
   - adaptive execution,
   - shuffle partitions,
   - eventuali flag legacy temporanei.

### Errori tipici da principiante

- script aggiornati solo parzialmente;
- mismatch tra conf Python job e conf cluster;
- query SQL funzionanti su vecchio runtime ma non su Spark 3.

## 3.4 Ordine consigliato di migrazione (molto pratico)

1. Migra bootstrap Spark (`SparkSession`) in `Ingestion.py`.
2. Adegua conf runtime e script submit.
3. Verifica lettura query + file list.
4. Testa validazioni nomenclatura/XSD.
5. Testa un flusso completo end-to-end.
6. Estendi test agli altri flussi.
7. Solo dopo fai tuning performance.

## 4. Test da prevedere (spiegati per chi parte da zero)

## 4.1 Unit test - test piccoli e veloci

- parsing argomenti (`Main.py`/`Params.py`),
- validazione nomenclatura file,
- funzioni utility (estrazione codici, campi derivati).

## 4.2 Integration test - test end-to-end

- run completo su almeno 2 flussi reali (es. A01 e SM1),
- confronto Spark2 vs Spark3 su:
  - numero file validi/scartati,
  - numero record dettaglio,
  - numero record principali,
  - partizioni scritte.

## 4.3 Test non funzionali

- tempo esecuzione,
- uso memoria/shuffle,
- stabilità su run ripetute.

## 4.4 Criteri di accettazione finali

1. Output funzionale coerente con baseline legacy.
2. Nessun errore runtime Spark 3 su flussi testati.
3. Scrittura parquet/Hive e `MSCK REPAIR TABLE` funzionanti.
4. Esecuzione stabile su almeno 3 run consecutive.

## 5. Glossario minimo (per orientarti subito)

- **Batch job**: processo che elabora dati a blocchi e termina.
- **SparkSession**: interfaccia principale Spark moderna (sostituisce i context legacy).
- **HiveContext/SQLContext**: API storiche Spark 1/2, da superare in Spark 3.
- **XSD**: schema XML usato per validare i file.
- **Partizione**: suddivisione dati in output per migliorare gestione/performance.
- **Baseline**: risultato di riferimento pre-migrazione usato per confronto.
